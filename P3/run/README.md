# P3/run — the continuous-run harness (H-1, hardened by H-3, H-4a, H-4b and H-5)

Design: `P3/design/continuous-run-harness-proposal-2026-09-22.md` (ratified 2026-09-22). Rules: runbook amendment F in `.claude/skills/p3-implementation/SKILL.md`. Per-sitting contract: `sitting-prompt.md` (appended to every headless sitting's system prompt). H-3 (deterministic limits, update guard, measured cap): `P3/reports/H-3-execute.md`. H-4a (main guard + landing tags, gate C2a): `P3/reports/H-4a-execute.md`. H-4b (evidence-gated evaluation, gate C1a): `P3/reports/H-4b-execute.md`. H-5 (Ctrl-C reaches the sitting): `P3/reports/H-5-execute.md`.

| File | Role |
|---|---|
| `loop.sh` | the supervisor: `flock`, STOP/RESUME files, orphan reap, the main guard (no sitting while CI on `main` is running or not green), launch a sitting, classify, record the ledger row + apply the cap rule, archive LIMIT evidence, tag a landing `sitting/<ts>`, act (sleep / switch model / wait for a gate / breakers); the sitting runs in its own process group, and Ctrl-C/SIGTERM on the loop stops it (see "Stopping") |
| `sitting.sh` | one budgeted headless sitting: `claude -p "continue implementation" …` with the wall clock (`timeout --signal=INT`) and `--max-turns` rails, `DISABLE_AUTOUPDATER=1`, the CLI update guard, and the measured cap in the launch prompt; forwards SIGINT/SIGTERM to `timeout` (H-5); `--smoke` = one-turn launch-line check |
| `lib.sh` | shared library: `classify`, `parse_reset_epoch`, `limit_retry_json`/`retry_reset_epoch`/`limit_epoch`, `notify`, `gate_answered`, `reap_orphans`, `sitting_ts`, `archive_limit`, `read_cap`/`record_sitting`/`update_cap`, `ci_state`, `tag_landing`, `proc_alive` |
| `test-classify.sh` + `fixtures/` | unit tests on canned results (limit text, 429, StopFailure status, status outcomes, crash, api_error, max-turns→CAPPED, reset parsing, gate marker, `--dry-run` decisions, `system/api_retry` limits, the StopFailure hook command run in isolation + its matcher), the verdict gate run in isolation on temp git repos (Write/Edit/Bash arms, missing/red/stale evidence, worktrees, its matcher), and `battery.sh` on temp Go modules (legs, evidence file, red legs, the web decision, worktrees, the wait) |
| `test-loop.sh` | loop/sitting tests with a stub `claude` and a stub `gh`, every loop in a temp repo with a temp bare origin: breakers, LIMIT archive, update guard (drift → probe fail/pass), measured cap (down, up, broken streak, clamps, prompt injection), main guard (red, queued/in progress, RESUME, STOP, notify once per run, gh absent/erroring/no runs, `P3_CI_GUARD=0`), landing tags (landed, progress-only, crash, bookkeeping-only, push failure), a gate answered in its file ending the GATE wait, the stop paths (H-5: SIGINT to the loop, Ctrl-C to its whole group, SIGTERM, a sitting that ignores SIGINT, the wall-clock rail) |
| `fixtures/observed/` (committed dir) | raw evidence of every LIMIT-classified sitting, `<sitting ts>/{result.json,status.json,api_retry.jsonl,class.txt}` — real observations to promote into tests |
| `cap` (committed) | the measured packet cap, default `3`, range 1..5; the loop rewrites it (shows as a working-tree change) |
| `cli-version.pinned` (committed) | the Claude Code version the harness last passed a probe on; the update guard rewrites it after a passed drift probe |
| `battery.sh` | the evidence battery (H-4b): `battery.sh <worktree>` waits out any other `go test` on the host, runs the CI legs serially on that worktree and writes `log/evidence/<branch>-<sha>.json` in the main checkout; exit 0 iff green |
| `hooks/verdict-gate.sh` | the PreToolUse verdict gate (H-4b): refuses a Write/Edit/Bash that puts `VERDICT: PASS` into `P3/reports/*-evaluate.md` unless that worktree's HEAD has green evidence |
| `hooks.proposed.json` + `install-hooks.sh` | the four project hooks (StopFailure / PreCompact / PermissionDenied / PreToolUse verdict gate) and their one-command installer |
| `sitting-prompt.md` | the sitting contract (budget, gate files, `status.json` last; the launch prompt's cap overrides its default) |
| `log/` (gitignored) | `sitting-<ts>.jsonl` stream-json transcript, `.err`, `.meta`; `loop.log`; `sittings.tsv` (the cap ledger); `compactions.log`, `denials.log` (hooks); `evidence/<branch>-<sha>.json` (`battery.sh`, one per tested commit) |
| `status.json`, `STOP`, `RESUME`, `loop.lock`, `loop.pid` (gitignored) | runtime signals |

## Run it

```bash
P3/run/test-classify.sh                     # 117 checks, no API calls (its battery.sh cases build tiny temp Go modules: run it while no battery runs)
P3/run/battery.sh <worktree>                # the evidence battery on that worktree's HEAD, foreground (waits out any other go test on the host)
P3/run/test-loop.sh                         # 147 checks with a stub claude + stub gh (breakers, LIMIT archive, update guard, measured cap, main guard, landing tags, gate wait, stop paths)
P3/run/sitting.sh --smoke                   # one 1-turn call: proves auth, flags, model string, log capture
tmux new -s p3loop 'P3/run/loop.sh --once'  # H-2(a): ONE supervised sitting, then exit
tmux new -s p3loop 'P3/run/loop.sh'         # H-2(b): unattended chain
touch P3/run/STOP                           # stop before the next sitting; the running one finishes normally
# Ctrl-C in the p3loop window: the running sitting ends its turn now (≤90 s, then SIGTERM), the loop exits 130; see "Stopping"
touch P3/run/RESUME                         # end a gate/blocked wait without editing the gate file; during a CI wait: start one sitting anyway
git tag -n1 -l 'sitting/*'                  # the landing tags with their landed lists (rollback: see "Main guard + landing tags")
```

`test-loop.sh` never touches the real repo, its origin or this checkout's runtime files (`status.json`, `STOP`, `RESUME`, `log/`, `loop.lock`): every loop runs in a temp repo with a temp bare origin (`P3_ROOT` overridden, the harness files copied in). Its loops still call `reap_orphans`, which kills any `go test`/vitest on the host, so run it only when no battery is running.

**Hooks (operator installs once, one command):** `P3/run/install-hooks.sh` merges `hooks.proposed.json` into the project `.claude/settings.json` — `StopFailure` (matcher `rate_limit|usage_limit|.*limit.*`: the two documented kinds explicitly plus any future error type containing `limit`) writes `status.json` = LIMIT (the loop then never guesses from prose), `PreCompact` logs every compaction to `log/compactions.log` (a sitting that compacts is over budget — the input of the measured cap), `PermissionDenied` logs what auto mode blocked to `log/denials.log`, `PreToolUse` (matcher `Write|Edit|Bash`) runs the verdict gate (see "Evidence-gated evaluation"). The coordinator cannot install these itself (its edit of settings.json is denied as self-modification). After changing `hooks.proposed.json`, re-run the installer.

**Stopping (H-5).** Two ways, by urgency:
- `touch P3/run/STOP`: the running sitting finishes normally and is classified, recorded and tagged as usual. The loop exits 0 before the next sitting starts, or at once if it is waiting (CI, gate, blocked, limit probes).
- Ctrl-C in the `p3loop` window, or SIGTERM to the loop (`kill $(cat P3/run/loop.pid)`): the loop sends SIGINT to the sitting's process group. `sitting.sh` forwards it to `timeout`, which passes it once to `claude` and claude's group. `claude -p` ends its turn on SIGINT and exits 0: the clean stop. The loop waits up to `P3_INT_GRACE` s (90) for the sitting to end. If it is still running, the loop sends SIGTERM, which `sitting.sh` sends on to `timeout`'s whole group, and waits up to 10 s more. Then the loop exits 130. A second Ctrl-C during the grace only logs `signal: already stopping — ignored`. Between sittings Ctrl-C exits 130 at once during a pause or wait, and after it returns during a model probe or CI read (those run under their own `timeout`, at most 120 s / 60 s). A sitting stopped this way is not classified, not added to the ledger and not tagged: the next sitting recovers from git.
- `loop.log` shows the path: `signal INT: SIGINT to the sitting's process group <pgid> …`, `sitting.sh: forwarding SIGINT to timeout <pid>`, on the slow path `sitting still running after 90s — SIGTERM to its process group …` and `sitting.sh: forwarding SIGTERM to timeout's process group …`, then `signal: sitting ended (sitting.sh exit=<n>) — loop exiting`. The sitting's `.meta` `exit=` is `timeout`'s status: on this host 124 after any stop that `timeout` signalled, the wall clock included. Every sitting also logs `sitting.sh exit=<n> (informational only)`.
- If a sitting ever outlives a stop (the loop logs `still running 10s after SIGTERM`), stop its `claude` by hand, the stop that worked on 2026-10-08: `pkill -INT -f '^claude -p .*--name p3-sitting-'` (it matches the `claude` process only, not `timeout`). Without that, `timeout --kill-after` sends SIGKILL 15 min after the first signal.
- *Why (defect 2026-10-08).* Before H-5 the loop started the sitting as a background job of a shell without job control. Such a job has SIGINT ignored, which `sitting.sh` cannot undo, and it stays in the loop's process group. `timeout` also moves itself and `claude` into a process group of their own. So neither the terminal's Ctrl-C nor the loop's `kill -INT <sitting.sh>` reached `claude`. The loop logged the forward twice and the sitting kept running until SIGINT was sent to the `claude` pid by hand. Now the loop turns on job control (`set -m`) for the launch only, so the sitting leads its own process group with default SIGINT, and `sitting.sh` traps INT/TERM and forwards them. The wall-clock rail was never affected: `timeout` installs its own SIGINT handler, and `claude` starts with default SIGINT (measured: SigIgn 0).
- *This host's `timeout` is uutils coreutils 0.8.0, not GNU.* Measured 2026-10-08: after the first signal it passes on no other until `--kill-after`'s SIGKILL, a signal to its whole group reaches `claude` twice (directly, then again from `timeout`), and it exits 124 after any signalled stop. Hence INT goes to the `timeout` pid only and TERM to its whole group. Re-check this if coreutils changes.

**After a limit:** the loop sleeps until the reset (or backoff 15 min → 1 h), then sends a one-turn canary (`probe_model`) every 15 min until the limited model answers; the Fable→Opus switch reverses only after a Fable probe completes. Every LIMIT-classified sitting's result line, `status.json` and `api_retry` events are copied to `fixtures/observed/<ts>/`. Budget rails cut a sitting before its wind-down → `CAPPED` (treated as CONTINUE; the next sitting recovers from git). A non-limit API failure (auth wall, overload) → crash class with backoff; three in a row stop the loop. Note `--system-prompt-snapshot` defaults to on: editing `sitting-prompt.md` mid-sitting has no effect until the next sitting.

**Update guard (H-3b):** every sitting runs with `DISABLE_AUTOUPDATER=1`. Before launch, `sitting.sh` compares `claude --version` with `cli-version.pinned`. On drift it runs the one-turn probe on the sitting's model: probe fails → `status.json` = `{"outcome":"BLOCKED","note":"CLI drift <old>→<new>: smoke failed"}`, exit 3 (the loop notifies and waits for `RESUME`); probe passes → log, one notification, the pin is updated, the sitting continues.

**Measured cap (H-3c):** after every sitting the loop appends one row to `log/sittings.tsv`: `ts model duration_s turns landed compactions transcript_bytes outcome cap` (landed = `status.json` `.landed` length; compactions = `compactions.log` entries inside the sitting's start/end window, interactive ones excluded; `cap` = the cap that sitting ran under, so the rule survives loop restarts and `--once`). Rule: any compaction → `cap` − 1 (min 1); the last five rows all ran at the current cap, landed it, and compacted zero times → `cap` + 1 (max 5). A preflight-blocked sitting (no transcript) writes no row. `sitting.sh` puts "land at most <cap> packets this sitting" in the launch prompt; the contract says that overrides its default of 3.

**Main guard + landing tags (H-4a, gate C2a):** the gate record is `P3/gates/harness-hardening-gate.md` item 2, answer (a): sittings keep pushing `main` directly, behind two guards.
- *Guard.* Before every sitting (`--once` included) the loop reads the latest CI run on `main` with `gh run list --branch main --limit 1 --json status,conclusion,headSha,url` (run in `P3_ROOT`, 60 s timeout, prompts and update notices off). `completed` + `success` → the sitting starts (`CI on main: success <headSha>` in `loop.log`). Any other status (`queued`, `in_progress`, `waiting`, `requested`, `pending`) → wait, re-check every `P3_CI_POLL` s. `completed` with any other conclusion (`failure`, `cancelled`, `timed_out`, `startup_failure`, …) → one notification per run ("P3 loop waiting: CI on main <conclusion>", the run URL as the body; a newer red run notifies again), re-check every `P3_WAIT_POLL` s. During either wait, `STOP` ends the loop and `RESUME` starts one sitting anyway; the next sitting is guarded again. No `gh` on PATH, a `gh` error (auth, API, timeout, an ambiguous repo) or no runs on `main` → `CI guard: <reason> — proceeding` and the sitting starts: the guard fails open by design, so grep `loop.log` for `CI guard:` to see when it did. `P3_CI_GUARD=0` disables it (the `LOOP start` line shows `ci_guard=`). CI runs on pushes to `main` and on PRs only, so a tag push starts no run. The guard sees the newest run GitHub has created; its `headSha` is logged for comparison with `git rev-parse origin/main`.
- *Landing tags.* After every sitting, before any exit (`--once`, breakers and DONE included): if `status.json` `.landed` is non-empty, or the sitting committed anything beyond STATE/HANDOFF bookkeeping (`progress_since`), the loop puts the annotated tag `sitting/<ts>` on the post-sitting HEAD. `<ts>` is the sitting's transcript timestamp (`log/sitting-<ts>.jsonl`, as `archive_limit` uses it), and the message is the landed list (`P3-TQ-4d, H-4b`; without one, `no landed list; commits beyond bookkeeping <before>..<after>`). Then it runs `git push origin refs/tags/sitting/<ts>`. A tag or push failure is logged (`TAG … failed: …` / `TAG … created, push failed: …`) and never stops the loop. A bookkeeping-only sitting gets no tag. The push uses whichever `gh` account is active (git's credential helper is `gh auth git-credential`), so a 403 there means the wrong active account.
- *Rollback.* Landings are `--no-ff` merges, so the plain range revert `git revert --no-commit sitting/<a>..sitting/<b>` stops at the first merge ("is a merge but no -m option was given"). Stop the loop (`touch P3/run/STOP`), then revert the first-parent commits instead: `git revert --no-commit -m 1 $(git rev-list --first-parent sitting/<a>..sitting/<b>)`, then `git commit -m "Roll back the sittings after sitting/<a> through sitting/<b>"`. This undoes everything after tag `<a>` up to tag `<b>`. On git 2.53 the index then equals the tree of `sitting/<a>` when `<b>` is HEAD. `git revert --abort` drops a half-applied revert.
- A running loop keeps the code it started with. Restart it to get the guard: `touch P3/run/STOP`, let the sitting end, relaunch. A future tag-triggered workflow (the release pipeline, S01.11) must match only its own tags (e.g. `v*`), never `sitting/*`.

**Evidence-gated evaluation (H-4b, gate C1a):** the gate record is `P3/gates/harness-hardening-gate.md` item 1, answer: all three parts. The process rules are runbook amendment G (`.claude/skills/p3-implementation/SKILL.md`): the spot-check signs the acceptance contract into the brief (`P3/prompts/spotcheck.md`), the evaluator grades against it and needs green evidence for a PASS (`P3/prompts/evaluate.md`), and every triage DROP records its falsification command and output. The two mechanisms:
- *Battery.* `P3/run/battery.sh <worktree>` (any path inside the worktree) first waits while another `go test` runs on the host: it polls `pgrep -f '[g]o test '` every `P3_BATTERY_POLL` s, ignoring its own ancestor processes, because a caller's shell can name `go test` in the same command line. Then it runs the legs in CI order, each from the worktree root, without stopping at a red one:
  - `clean`: no tracked change and no untracked file outside `P3/reports/`. Commit first and delete probe files; a report draft may stay.
  - `web-install` (`npm ci --ignore-scripts`), `web-typecheck`, `web-test`, `web-build`, only when `web/src` differs between the merge base with `main` and HEAD.
  - `gofmt` over the tracked Go files, `vet`, `build`, `test` (`go test -p 1 -count=1 -skip "$P3_BATTERY_SKIP" ./...`), `lockgate` (`go run ./tools/lockgate`).
  - `stable`: HEAD did not move during the run.

  It writes `<main checkout>/P3/run/log/evidence/<branch>-<sha>.json`. The main checkout is the parent of `git rev-parse --git-common-dir`, so a worktree's evidence lands in the main checkout's gitignored `log/`. A `/` in the branch name becomes `_`, and a detached HEAD is `detached`. Fields: `branch`, `head`, `ok` (every leg green), `worktree`, `web` (`skipped: …` or `ran: …`), `skip`, `legs[]` (`name`, `ok`, `rc`, `secs`; a red leg adds its last 20 output lines as `tail`; the test leg adds `pkgs_ok`, `pkgs_notest`, `pkgs_fail`, `tests_failed`), `logs` (the full leg output, a `${TMPDIR:-/tmp}/p3-battery.*` dir), and `times` (`started`, `finished`, `waited_s`, `total_s`). A rerun on the same commit overwrites the file, so the latest result counts. Exit 0 iff `ok`; usage error or not a worktree: 2. A full run on this repo takes minutes; an agent runs it in the foreground, or in the background and reads the result before writing a verdict.
- *Gate.* `hooks/verdict-gate.sh` is a PreToolUse hook with matcher `Write|Edit|Bash` and a 30 s timeout. It acts only when two things hold:
  - the target is a `P3/reports/*-evaluate.md` file: the Write/Edit `file_path`, or for Bash any such path in the command (a relative path resolves against the hook input's `cwd`, or against a leading `cd <dir> &&`);
  - the text matches `VERDICT: PASS` (case-insensitive, `*`/`_`/backtick emphasis allowed): Write `content`, Edit `new_string`, or the Bash `command`.

  Then it requires `<main>/P3/run/log/evidence/<branch>-<HEAD>.json` with `ok: true` and `head` equal to the HEAD of the report's worktree. Without it, the hook exits 2 and puts the reason plus the exact battery command on stderr. Everything else exits 0 with empty stdout. A FAIL verdict needs no evidence. Any commit after the battery (the report commit included) needs a new run before another PASS write.
- *Contract, verified 2026-10-07 against the Claude Code 2.1.292 hooks reference (code.claude.com/docs/en/hooks):*
  - stdin carries `cwd`, `tool_name` and `tool_input`, and Write/Edit `file_path` "is always absolute";
  - exit 2 "Blocks the tool call", and "Claude sees the stderr message as the denial reason";
  - exit 1 and other codes do not block, and "A timed-out `command` … hook doesn't block the tool call";
  - a missing script exits 127 with a non-blocking notice, which leaves the gate off, so watch for `PreToolUse hook error` after installing;
  - hooks "also run inside subagents";
  - in a worktree "`${CLAUDE_PROJECT_DIR}` stays put" (the script runs from the main checkout) while "`cwd` follows Claude".
- *Why Bash too.* Auto mode, which every headless sitting runs under, steers agents to change files through Bash. The P3-TQ-8 evaluator wrote and re-checked its report with `cat > …-evaluate.md <<'EOF'`, `cat >>` and a `python3` edit, so a Write/Edit-only gate would have seen none of it. The Bash arm reads only the literal command: a PASS that never appears in it (`cp draft.md …-evaluate.md`, `sed -i s/FAIL/PASS/`) gets through. That is why the coordinator's landing check (amendment G2) reads the evidence file itself.
- *False positives.* A read-only command that names an evaluate report and contains `VERDICT: PASS` (`grep 'VERDICT: PASS' P3/reports/x-evaluate.md`) is refused while that worktree's HEAD has no green evidence, so search for `VERDICT` alone. Any write that quotes a PASS verdict needs evidence too.
- *Install.* After the merge the operator re-runs `P3/run/install-hooks.sh`. It adds the `PreToolUse` key: the project settings have none today, and user-level hooks are separate and stay as they are. Edits to settings files are normally picked up by the file watcher. A sitting running at install time may need its next start.

Environment knobs (defaults in `lib.sh`): `P3_MODEL_PRIMARY` (`claude-fable-5-1[1m]`), `P3_MODEL_FALLBACK` (`claude-opus-5`), `P3_SITTING_WALL` (`4h`), `P3_SITTING_MAX_TURNS` (`600`), `P3_SITTING_MAX_BUDGET_USD` (empty = no nominal-cost rail on the subscription lane), `P3_PROBE_INTERVAL` (`900`), `P3_PAUSE_MIN`/`P3_PAUSE_MAX` (`120`/`1800`, idle backoff), `P3_CRASH_PAUSE` (`300`), `P3_SWITCH_PAUSE` (`60`), `P3_NOTIFY_URL` (optional ntfy.sh topic for phone push), `P3_CI_GUARD` (`1`; `0` = no main guard), `P3_CI_POLL` (`120`, re-check while the CI run on `main` is queued/in progress), `P3_WAIT_POLL` (`600`, re-check of every other wait: gate, blocked, CI on `main` not green), `P3_INT_GRACE` (`90`, seconds a sitting gets to end its turn after Ctrl-C/SIGTERM on the loop before SIGTERM). In `battery.sh`: `P3_BATTERY_SKIP` (`TestLivePhraseAndSummarize|TestLiveIntakeTriageClassifiesWebshop`, the GPU-live tests), `P3_BATTERY_POLL` (`30`, re-check while another `go test` runs). State-file paths (the tests point them at a temp dir): `P3_CAP_FILE` (`P3/run/cap`), `P3_SITTINGS_TSV` (`log/sittings.tsv`), `P3_COMPACTIONS_LOG` (`log/compactions.log`, must match the PreCompact hook's path in real runs), `P3_CLI_PIN` (`P3/run/cli-version.pinned`), `P3_OBSERVED_DIR` (`P3/run/fixtures/observed`).

## How a sitting is classified (never by exit code)

1. A usage-limit signature in the final `{"type":"result"}` line (`api_error_status` 429, or the limit regex in `result`/`error`) → `LIMIT:<family>:<reset epoch>`. The reset epoch is the prose time when one parses, else the last limit-kind `system/api_retry` event's time + `retry_delay_ms` (the event's `timestamp` if present, else the transcript's mtime), else 0. Fable limit while on the primary model → the next sittings run on the fallback until the reset (or 1 h); any other limit → sleep until the reset, else backoff 15 min → 1 h.
2. Else the sitting's own `status.json` (its last act, or the StopFailure hook's LIMIT record, with the same epoch fallback): `CONTINUE` → next after 2 min; `GATE:<file>` → desktop notification, poll the file for `answered: yes|partial` every `P3_WAIT_POLL` s (10 min); `BLOCKED` → notification, wait for `RESUME`; `DONE` → exit 0.
3. Else, if the sitting ended while still retrying a limit (its last assistant/`api_retry` event is an `api_retry` whose `error` kind contains `limit`) → `LIMIT` (covers a wall-clock kill mid-retry with no result line). A limit retry the CLI recovered from does not count.
4. Else `CAPPED` (budget rail) or `CRASH` (no signature): 3 consecutive crashes → stop + notify. Stall breaker: 3 consecutive sittings without progress beyond STATE/HANDOFF bookkeeping commits → stop + notify; the pause between unproductive sittings grows 2 min → 10 min → 30 min. A LIMIT never counts as a crash or a stall.

Never run an interactive `continue implementation` session while the loop is up: touch `STOP` first, wait for the sitting to end (`tmux attach -t p3loop`), then work interactively.
