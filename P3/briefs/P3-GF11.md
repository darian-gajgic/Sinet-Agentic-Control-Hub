## 1. The defect, precisely (all first-hand this session)

Two defects, one wall:

**D-1 — the accept cannot LAND on a remote-less store.** The chain:

1. The New-project door creates local-only stores by construction. Over HTTP the door cannot
   express a clone source (`internal/shell/project_seams.go:163-166` — "every onboarding started
   here initializes a fresh store") and the `remote_url` body member is optional stored data,
   never dialed (`internal/api/projects.go:594-599`; `internal/project/onboard.go:51-52`). The
   walker left it empty ("decide later"). `Onboard` with `Source:""` runs `initRepo` + one
   `--allow-empty` init commit (`onboard.go:109-120`) and `Register` stores `remote_url:""`,
   stamping `has_remote:false` into the registration audit event (`registry.go:62-67`).
2. The accept's execute phase composes a broker push with `Remote: e.RemoteURL`
   (`internal/accept/accept.go:483-489`) — for a door-minted project that is `Remote: ""`.
3. The broker refuses before touching git: `if req.Remote == "" { return Response{OK:false,
   Error:"push with no remote"} }` (`internal/broker/git.go:65-67`). The refusal is CORRECT for
   the broker — a push request with no remote is malformed — the defect is that the accept
   composed it at all.
4. `broker.Client.Push` collapses the !OK response to `fmt.Errorf("broker: %s", resp.Error)`
   (`client.go:121-123`); `executeAccept` fails the effect and wraps
   (`accept: broker push: %w`, `accept.go:490-493`).

**D-2 — the refusal reached the wire as a raw 500.** `handleAccept` hands the error to
`s.writeSurface(w, nil, s.reviewErr(err))` (`internal/api/accept.go:534-539`); `reviewErr` maps
only `internal/review` sentinels by type and answers everything unmarked with
**500 `internal` + `Msg: err.Error()`** (`deliverables.go:770-790`) — the raw internal chain
(`accept: broker push: broker: push with no remote`) is served as the response detail. That is the
§38 posture bypassed at the accept seam: a legitimate act on a legitimately-configured project got
a crash-shaped answer with an internal error chain on the wire, no door-state change, and the card
still honestly-OPEN (`acceptable()` never probes the push seam — `accept.go:269-289` — walk E3).

**What the walker's three attempts left behind (the wedged-world analysis).** Per attempt:
`Propose` → `Approve` → `BeginExecute` → `AppliesClean` (clean, ref-free — `merge-tree
--write-tree` "NEVER touches the working tree or any ref", `internal/project/accept.go:38-43`) →
`SquashAccept` (writes ONE commit **object** via `hash-object -w`; "No ref is moved",
`project/accept.go:104-107,133-137`) → push refused → `failEffect(effectID,"push failed")`
(`accept.go:490-492`) → error out. So: **three FAILED effect rows, up to three dangling commit
objects (harmless; `gc.auto=0`), NO ref moved, `AdvanceDefaultBranch` never reached,
`review.Accept` never called, `markInflight` never reached** (it sits after the push,
`accept.go:505`), and the in-memory inflight map died with the process anyway. The deliverable is
`in-review` with an open, truthful card. **The world is CLEAN-RETRYABLE**: a fresh POST after GF11
runs the whole flow again (each accept proposes a NEW effect; nothing keys on prior failed rows —
`Accept` performs no such check, and `acceptedEffect` reads only `succeeded` rows,
`api/accept.go:632-650`). No migration, no repair verb.

## 2. What the spec actually requires — recorded reading, NO amendment

- **S13.6 step 2 is where the record is written; step 4 is transport.** Step 2: "One clean
  attributed commit …". Step 4: "**Push as the user** over broker-held SSH keys with explicit
  CAS" — every word of it defined over a remote and a credential. S13.6's High-tier parenthesis
  ("risk tier High — outward push") was ALREADY read arm-locally by the ratified P3-RW-17 cut
  (`accept.go:225-239`: the commit-push ceremony "is by its own text the outward arm for
  repo-targeted work"). No sentence in S13.6 makes a push constitutive of an accept on a store
  that HAS no remote; no sentence forbids a remote-less store.
- **S13.7 explicitly blesses the remote-less store.** "A v0 project without a repo gets one
  created/registered by the onboarding task" — documents "ride the identical machinery", and the
  registry's remote URL is one per-entry datum among others. `Register` treats `RemoteURL != ""`
  as a first-class boolean fact (`has_remote`) in the audit event.
- **S13.1 makes the platform-owned store the permanent record.** "Minted revision refs are
  retained in the platform-owned project store under a platform ref namespace"; the revision's
  content pin is the immutable record. S13.5: snapshot commits "never reach a user-facing
  remote" — the store is load-bearing without one.
- **S02.7's journal is for effects OUTSIDE the DB transaction's guarantee.** Its class-A exemplar
  IS `git push --force-with-lease`. A local landing (commit object + CAS `update-ref`) is not
  outward, but it IS a non-DB side effect — see R2 for what that settles.

**Amendment owed: NONE.** This is the RW-17 recorded-reading extended one step: the ceremony's
push step engages exactly where the registry records a remote; where it records none, the landing
is the attributed commit advanced onto the store's default branch — the same "permanent record"
S13.1/S13.7 name. If the executor finds spec text genuinely refusing this, the S00.9 door (dated
changelog entry + operator approval) is the honest landing — never a silent workaround.

## 3. The design cut

**The remote-less repo-backed accept is the SAME ceremony minus transport**: applies-cleanly
gate → trailers invariant (GF10 R6 — unchanged) → platform squash → **advance the store's default
branch** (`AdvanceDefaultBranch` — the CAS fast-forward verb that already exists,
`project/accept.go:147-180`) → deliverable accepted → sibling-accept freshness fires. No broker
request is ever composed.

**Where the knowledge of "no remote" lives, and who decides:**

- The ONE authority is the S13.7 registry entry (`repo_registry.remote_url`), which the accept's
  shared execute phase ALREADY reads (`executeAccept` line 457: `a.cfg.Project.Get`). The
  **accept orchestration decides** — in the shared execute phase, so a fresh accept and a
  crash-window re-drive take the same arm from the same read.
- The **broker stays byte-untouched**. Its no-remote refusal SURVIVES as the guardrail: a push
  request with no remote is malformed, and teaching the broker to no-op it "successfully" would
  silently mask a genuinely missing remote on a store that should have one (honest-absence), and
  would put registry knowledge into a component that deliberately imports no DB (CONVENTIONS §29,
  `git.go:16-17`).
- **"Deliberately local-only" vs "misconfigured" is structural at v0**: empty `remote_url` can
  only be the owner's door choice — the door's field is optional, `Register` records the choice
  (`has_remote`) in the audit event, and NO landed verb edits `remote_url` afterward (grep this
  session: writers are `Register`/`Onboard` only; `EditCommands` touches commands alone). A
  future remote-attach verb owes the distinction and the in-flight-effect revisit (OQ4).
- The accept CARD derives the same fact for its wire copy via a one-column SQL read beside the
  landed `protectedRef` read (`api/accept.go:401-417`) — `internal/api` imports neither
  `internal/project` nor `internal/broker` (§40-B wall, unchanged).

## 4. Requirements

- **R1 (the local landing).** A repo-backed accept on a project whose registry entry records no
  remote LANDS: applies-cleanly gate onto the depth-1 base, the GF10 trailer invariant enforced
  identically (empty engine/model/vendor still refuses before Propose), platform squash pinned to
  the approval timestamp, `AdvanceDefaultBranch` onto the store's default branch, deliverable →
  accepted (supersession included), sibling-accept freshness fired. **No broker request is
  composed on this arm, ever.** Where a remote exists the push arm is byte-identical to today.
  [S13.6 steps 1–3; S13.7; S13.1; walk E1]
- **R2 (the effect discipline — settled, with the reasoning).** The local landing goes THROUGH
  the class-A journal: Propose → Approve → BeginExecute → (squash + advance) → Succeed. Why not
  RW-17's no-journal shape: the pinned arm mutates ONLY DB rows, whose exactly-once is the
  transaction's own; the local landing mutates the git store — a side effect OUTSIDE the DB
  transaction, which is precisely the non-atomic shape S02.7's two-phase discipline exists for.
  It also keeps `acceptedReadBack`/`acceptedEffect` working unchanged (the retry read-back
  derives the commit from the succeeded effect row, `api/accept.go:614-650`) and gives the local
  arm the crash-window closure for free: `ReDrive`/`ReDriveApproved` replay via the SHARED
  execute phase; replay is idempotent because the squash is content-addressed and pinned to
  `ApprovedTS` (same bytes ⇒ same sha) and `AdvanceDefaultBranch` no-ops on already-incorporated
  shas. Mechanics: **the payload shape stays byte-identical** (GF10 §6 wall — the arm is selected
  at execute from the registry entry, not from a payload member; every field the payload pins is
  honored identically on both arms); the **Succeed result gains an additive member** naming the
  landing (recommended `"landing":"local"`), push-arm result bytes unchanged. [S02.7; S02.5;
  GF10 §6]
- **R3 (honest absence; the broker untouched).** `internal/broker` source is byte-untouched; the
  no-remote refusal stays and gains a pinned test (no landed test covers it — verified by grep
  this session). The accept layer never infers localness from anything but the registry entry's
  remote (not from `GitProfile`, not from URL scheme). A silent push no-op anywhere is a
  forbidden landing. [P-T12-1 posture; CONVENTIONS §29]
- **R4 (the wire says where the official copy lands).** `AcceptCard` gains an additive `landing`
  member: `"remote-push"` (push arm) / `"local-store"` (remote-less repo arm) /
  `"decision-record"` (RW-17 pinned arm). This is a FACT about the act, not a refusal taxonomy —
  `acceptable` + `reason` stay the ONE gate (GF10 S-3 stands). Arm-accurate copy, plain words:
  the local arm's open `reason` says the official copy is written into the project's **local
  store** on this machine; its tier statement keeps tier High (RW-17's uniformity reading:
  operator-visible relaxation later, never a silent one) and must NOT claim "this pushes a commit
  to a shared branch"; the success `Detail` states the local landing. `ProtectedRef` stays served
  on this arm (the branch IS advanced — it is a true target), derived via the landed one-column
  read. The FE rendering of `landing` (the walk's "Pushes to golden-crumb · refs/heads/main"
  consent sentence, walk E3) is the GF9 builder's; **GF11 touches NO web file** and declares the
  wire contract here. [S15.2 additive-first; B6-2A D9; walk E3]
- **R5 (the 500 dies).** The no-remote 500 becomes structurally impossible (R1: the request is
  never composed). For the push arm's REMAINING failure modes: a push the broker could not
  perform (refusal or transport failure — today both collapse to one error string) surfaces from
  `internal/accept` as a NAMED sentinel (recommended `accept.ErrPushFailed`, wrapping the cause)
  and `internal/api` maps it ON TYPE to a served answer — **502, code `push_failed`**, plain
  words stating the push could not be performed, nothing was accepted, the deliverable stays in
  review and the accept can be retried; the raw cause goes to the ops log only. The stale-lease
  path is untouched (a rejection is already a merge card, never an error). No error-string
  matching anywhere. [§38; S15.2; walk E2]
- **R6 (fixture faithfulness).** The api `fakePusher` must refuse `Remote == ""` exactly as the
  broker does (mirroring `git.go:65-67`) so the api suite can never again green a push request
  production refuses — the same fixture-gap family GF10 §2 documented for `mkRun`. (Grounding
  adds an additive `pushErr` field only; the executor makes the empty-remote refusal the fake's
  own default behavior.) The accept-package suite already runs the REAL broker; its new
  remote-less fixture is committed red at grounding. [GF10 §2 precedent]
- **R7 (concurrency).** The local arm preserves the depth-1 merge-queue semantics: a second
  accept during/after a local landing validates onto the advanced HEAD (or HEAD-plus-first), and
  a CAS failure from a concurrent local advance surfaces as the S13.6 collision answer (merge
  card / loud `ErrNotFastForward` mapped honestly), never a raw 500. Sequential stacking (two
  local-only accepts land, second parented on the first) is asserted. [S13.6 step 1; S02.8]
- **R8 (retryability of the wedged world).** Nothing is migrated and no repair verb is built: a
  failed no-remote attempt left only FAILED effect rows and unreferenced commit objects (§1), so
  the SAME deliverable on the SAME world accepts after GF11. The E5-rewalk evidence world stays
  stopped and kept as evidence; the acceptance headline runs on a fresh world per the STATE row
  (E5-REWALK-2), and same-world retry needs no special handling. [§1 analysis]
- **R9 (forbidden landings, by name).** Inventing/defaulting a remote; a broker push no-op;
  swallowing real push failures on remoted stores (they keep honest FAILED-effect handling, now
  served per R5); skipping the trailer invariant, the PIN step-up, the payload-hash pin, or the
  applies-cleanly gate on the local arm; a per-call "local" flag on the accept body (the arm is
  the registry's fact, never the caller's choice — the SigningPosture precedent); touching any
  adopted engine (adopt-don't-fork: this is OUR broker/accept/api code; the host git CLI stays
  consumed unmodified).
- **R10 (proof).** The four grounding-committed RED tests green at landing; executor-owned
  property tests (R3 broker pin, R7 stacking, R2 re-drive idempotence on the local arm); the full
  serial battery green; the operator's E5-REWALK-2 targeted re-walk is the acceptance headline.
