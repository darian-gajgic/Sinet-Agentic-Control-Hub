## BINDING carried facts (verified at grounding, 2026-07-29)

### A. LIVE-VERIFIED — the Declarative Web Push platform reality (mid-2026; current web sources, never memory)

1. **Support matrix.** Declarative Web Push (DWP) is **shipped and stable on Apple platforms only**: iOS/iPadOS 18.4 Home-Screen web apps (webkit.org/blog/16535, 2025-03-27) and macOS Safari 18.5 (webkit.org/blog/16923; WWDC25 session 235). Current Safari is **26.6 (released 2026-07-27)** with 27 beta; the 26.x feature posts contain **no push changes** — DWP unchanged since 18.5, still shipping. **Chromium/Chrome/Edge: NOT supported** (chromestatus.com API query returns zero results, fetched 2026-07-29; tracker issues.chromium.org/issues/382298314 exists but is login-walled — status UNVERIFIED). **Firefox: NOT implemented** (bugzilla 1935325 + 1946085 both status NEW via REST API, last changes 2025-09/10; Mozilla standards-position POSITIVE, mozilla/standards-positions#1176, Feb 2025).
2. **Backward compatibility is designed-in — one payload, two renderers.** A DWP JSON payload delivered to a classic-push browser arrives as the payload of the service worker's `push` event ("If it arrives to an older browser, it's handled imperatively by JavaScript as it always had been" — webkit.org/blog/16535); a legacy payload to a DWP browser is handled classically (the UA "opportunistically parses each incoming push message", w3c.github.io/push-api). **A classic-only browser (all Android/Chromium, Firefox, iOS 16.4–18.3) still requires a service-worker subscription — no no-SW subscribe exists outside Safari.** The spec's own S15.11 words already anticipate this split: "Android is standard push".
3. **The payload contract is now normative W3C Push API §3.3** (Working Draft 2025-12-01, w3.org/TR/push-api — DWP was merged into the Push API proper, w3c/push-api#360). Top level: **`web_push: 8030` (REQUIRED int — the RFC 8030 disambiguator), `notification` (REQUIRED object), `mutable` (optional bool)**. `notification` REQUIRED members: **`title`** and **`navigate`** (URL loaded when the notification is tapped); optional: `dir/lang/body/tag/icon/image/badge/vibrate/timestamp/renotify/silent/requireInteraction/data/actions` (each action carries its own `navigate`). **`app_badge`** is WebKit-SHIPPED inside `notification` (blog example: `"app_badge": "1"`) but **absent from the W3C WD text**; badge-only pushes (badge without visible notification) are **UNVERIFIED in shipped Safari** — v0 therefore ALWAYS sends a visible notification carrying `app_badge` alongside. `mutable` absent ⇒ NO SW event fires even if a SW exists — the UA displays directly; v0 sends immutable. Content disposition: the WebKit proposal keyed on `Content-Type: application/notification+json`, the merged WD parses opportunistically — **send both** (that header AND the 8030 field).
4. **Subscription flow.** Safari/DWP: **`window.pushManager.subscribe({userVisibleOnly: true, applicationServerKey})`** — PushManager on `window` (webkit.org/blog/16535 shipped code; the explainer's `navigator.pushManager` is the OLD proposal, not what shipped); subscriptions are origin-interchangeable with SW-created ones. Classic: `serviceWorkerRegistration.pushManager.subscribe(...)`; **Chrome/Edge reject without `userVisibleOnly: true`** (MDN, modified 2025-06-23). `pushsubscriptionchange` fires at the SW registration (WD §10.4); a window-scoped equivalent is UNVERIFIED. Notification permission required; Safari's user-gesture requirement is long-standing (flagged: not re-verified against a live page this session — the executor treats request-inside-gesture as mandatory anyway).
5. **VAPID (RFC 8292) is required in practice everywhere.** Apple: VAPID keypair mandatory; JWT exp ≤ 24 h, **refresh ≤ once/hour**; strict errors (BadJwtToken/BadVapidPublicKey/VapidPkHashMismatch); **TTL header required**; Urgency `very-low|low|normal|high`; Topic ≤ 32 base64url chars; **4 KB payload cap**; **"You don't need to join the Apple Developer Program to send web push notifications"** (developer.apple.com "Sending web push notifications in web apps and browsers"). Chrome/Edge require `applicationServerKey` at subscribe; Mozilla autopush enforces VAPID (post-CVE-2023-6868).
6. **iOS/macOS specifics.** iOS Home-Screen install is **still mandatory for any web push on iOS 26** (mobiloud.com iOS-PWA guide, updated 2026-02-13); iOS 26: every site added to the Home Screen opens as a web app by default (webkit.org/blog/17333). Classic push floor: iOS 16.4 / macOS 13 Safari 16. **Safari revokes push permission for invisible pushes** (Apple doc) — DWP makes invisibility structurally impossible; the classic leg must always `showNotification`. Badging is user-configurable in iOS notification settings.
7. **Chromium installability (the Android leg of the drill):** HTTPS + manifest with `name`/`short_name`, **icons 192px AND 512px**, `start_url`, `display` standalone-class (web.dev/articles/install-criteria, updated 2024-09-19); a SW is NO LONGER an install criterion — push itself still needs one.

### B. LIVE-VERIFIED — the server-side send/encryption reality (RFC 8030/8291/8292) and the rail verdict

1. **RFC 8291 (aes128gcm), what a sender implements** (datatracker.ietf.org/doc/html/rfc8291): per-message ephemeral **ECDH P-256** against the subscription's `p256dh` (65-byte uncompressed point) + 16-byte `auth` secret; **HKDF-SHA-256 twice** (extract with auth as salt → expand with `"WebPush: info" || 0x00 || ua_public || as_public` → 32-byte IKM; then extract with a fresh 16-byte salt → CEK 16 B via `"Content-Encoding: aes128gcm" || 0x00`, nonce 12 B via `"Content-Encoding: nonce" || 0x00`); **AES-128-GCM single record**, padding delimiter `0x02`; binary header `salt(16) || rs(4,BE) || idlen(1) || keyid(=sender 65-byte pubkey)` = 86 bytes; total ≤ 4096. **`aes128gcm` is the ONE current encoding** (browsers advertise it via `PushManager.supportedContentEncodings`; the legacy `aesgcm` draft is dead). **RFC 8291 Appendix A carries a COMPLETE worked example with every intermediate value** (ecdh_secret, PRK, IKM, CEK, NONCE, the 86-octet header, final ciphertext) — a step-by-step golden vector from the standard itself (verified this session).
2. **RFC 8292 (VAPID):** ES256-signed JWT (ECDSA P-256 — MUST), `aud` = origin of the push resource URL, `exp` ≤ 24 h, `sub` contact; header `Authorization: vapid t=<jwt>, k=<base64url uncompressed pubkey>`. TTL/Urgency/Topic are RFC 8030 headers. **Apple's service accepts plain RFC 8030+8291+8292** — standard web push, no APNs credentials.
3. **STDLIB VERDICT: a complete, correct send path is implementable in PURE Go stdlib at this repo's Go 1.26.5 — no gap.** `crypto/ecdh` (stdlib since 1.20; `NewPublicKey` parses the 65-byte `p256dh` directly), **`crypto/hkdf` (stdlib since Go 1.24** — go.dev/doc/go1.24), `crypto/aes`+`crypto/cipher` GCM, `crypto/ecdsa` for ES256 — **`SignASN1` is the WRONG shape for JWS; use `ecdsa.Sign`'s `(r,s)` + `big.Int.FillBytes(make([]byte,32))` for the raw 64-byte R‖S**; the JWT is `base64.RawURLEncoding` hand-assembly; `net/http` does the RFC 8030 POST. **`golang.org/x/crypto v0.54.0` is ALREADY a direct, locked dependency** (components.lock:104, module claim `golang.org/x/crypto`, role currently argon2-only) — available as fallback, not needed.
4. **Library candidates (pre-walked for OQ1):** **github.com/SherClockHolmes/webpush-go v1.4.0** — MIT, tag 2025-01-02, NOT archived, commits through 2026-04-22 (untagged above v1.4.0), aes128gcm-only, deps `golang-jwt/jwt/v5` + `x/crypto` (floor v0.31.0 — satisfied by the repo's v0.54.0; adoption would add ONLY golang-jwt as a new module), imported-by 177, no advisory surfaced against it (v1.4.0 remediated its dep's CVE-2024-51744 by upgrade). **github.com/marknefedov/go-webpush** v2 — MIT, `go 1.26`, sole dep golang-jwt (stdlib crypto), young/low-adoption; v1.0.3 2025-09-06. GoogleChrome/push-encryption-go is ARCHIVED (points at webpush-go).
