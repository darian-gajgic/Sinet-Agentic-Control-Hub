3. **Intake-card cancel** (`internal/intake/answer.go` :121, :724): same shape as 2 — human ledgered, transition `Actor: run.ActorPlatform`.

### Requirements

## D2 — deliverable mint leaves `project_id` empty

### Root cause (first-hand)

S13.1's row contract: "`deliverables` | task ref, **project ref**, type, …". The schema has the column (`NOT NULL DEFAULT ''`), `EnsureInput` has the field, and BOTH mint call sites omit it: `reviewSink.ensure` (`internal/stage/review_sink.go` :86) and `presentDefinition` (:51). The project IS known at mint time — the walk task's intake request carries `"project":"parts-catalog"`, its execute leg got a `worktrees/parts-catalog/<task>` workspace, and `task_project` (SQL view, migrations 0016/0022/0023: approved claims → intake registry pin → onboarding id) resolves `t-1e211253dfa21c28 → parts-catalog` in the evidence world today.

**Blast radius (walk-proven):** `internal/api/accept.go` `acceptable()` :275 — repo-backed revision (`SnapshotSHA != ""`) + `d.ProjectID == ""` → `"this deliverable belongs to no project, so there is no protected ref to push to (S13.7)"`; the accept door refuses a deliverable the platform itself minted from a project worktree. The tasks view already works around the same absence by joining `task_project` (reads.go :605–:617, with the "SAME expression" rule stated in its comment).

### Requirements

- **D2-R1 (mint fills it).** `EnsureDeliverable` (`internal/review/store.go` :101) resolves an empty `in.ProjectID` at INSERT through the same expression the views use: `COALESCE(NULLIF(?,''), (SELECT project_id FROM task_project WHERE task_id = ?), '')`. An explicitly passed ProjectID wins; a task with no registered project stays honestly `''`. No new seam, no producer import — the edge is schema data, and it CANNOT disagree with the views because it IS the view (the reads.go §37 precedent).
- **D2-R2 (reads heal history).** The store's deliverable reads (`Deliverable`, and every `SELECT … FROM deliverables` the store or `internal/api` serves a `ProjectID` from — grep for it) serve `COALESCE(NULLIF(d.project_id,''), tp.project_id, '')` via `LEFT JOIN task_project tp ON tp.task_id = d.task_id`. This is the serve-time task-join fallback: the accept door, the card, and the views see the truth for EXISTING rows (the live walk row `dlv-t-1e211253dfa21c28`) with zero data rewrites. `acceptable()` itself needs no change — it reads `d.ProjectID`.
- **D2-R3 (backfill decision — recommended and reasoned).** **Serve-time fallback + mint-forward. NO migration, no one-time UPDATE.** Reasons: (a) migrations 0001–0024 are immutable and a new data migration would freeze a DERIVED fact into rows — the task_project edge can legitimately sharpen later (claims at plan approval supersede the triage pin), and a frozen copy goes stale; (b) the read-side COALESCE serves every consumer today at the cost of one LEFT JOIN against a small table; (c) a write-side backfill adds a write path for zero additional serving truth. If the executor concludes a migration is truly forced (it should not be), STOP and flag — that is OQ2, an operator call.

### Requirements

Recommended SQL shape (one row per task, latest cancel event, both predicate legs so pre-parity history lists):

  ```sql
  SELECT t.task_id, t.user_id, t.title, MAX(e.event_seq) AS event_seq, e.ts AS cancelled_ts,
         COALESCE(json_extract(e.payload,'$.detail.actor'),
                  NULLIF(json_extract(e.payload,'$.actor'),'platform')) AS cancelled_by,
         json_extract(e.payload,'$.reason') AS reason
    FROM tasks t
    JOIN runs r        ON r.task_id = t.task_id
    JOIN run_events e  ON e.run_id = r.run_id AND e.type = 'run.state_changed'
                      AND (json_extract(e.payload,'$.detail.cause') = 'human cancel (4.5)'
                           OR instr(COALESCE(json_extract(e.payload,'$.reason'),''), '(4.5)') > 0)
   WHERE t.kanban_status = 'cancelled' [+ scoped("t.user_id")]
   GROUP BY t.task_id ORDER BY event_seq DESC LIMIT ?
  ```
