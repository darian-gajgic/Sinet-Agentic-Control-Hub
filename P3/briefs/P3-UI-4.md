## 4. Requirements B — the C-1 fix (login reachable in dev posture; Sign out honest)

**The finding** (gate §9 C-1, verified live at the gate): in dev posture the header's Sign out is a no-op and /login is unreachable. **Root cause, in the landed code:** `App.tsx:86–97` fails closed in both directions — "no /login once there is a session" — while `SessionAuthenticator` (identity.go:83–97) resolves every session-less request to `Identity{UserID:"dev", Dev:true}` in dev posture, so there is ALWAYS a session, the picker can never render, and `api.logout()` (App.tsx:136–139) clears nothing that matters — the re-read resolves to the dev identity again. The identity layer's own note — "sessions still win when present, so the full login flow is exercisable in dev" (identity.go:74–76) — is defeated one layer up. **Production posture is unaffected** (no fallback; both arms behave). The wire truth (auth_handlers.go:91–116): the dev-fallback session serves `{authenticated:true, dev:true}` with **no `user` object**; a real session serves `{authenticated:true, user:{…}}` with `dev` omitted; real cookies ALWAYS win (identity.go:84–92); logout revokes + clears the cookie (auth_handlers.go:166–175) and the next resolve falls back to dev (dev posture) or anonymity (production).

- **R10 — the /login arm carves out the dev fallback, exactly.** `session.dev === true` ⇔ the resolved identity IS the fallback (the one place the server sets it). The bounce-away-from-/login arm becomes `authed && session.dev !== true && route.id === 'login'`. Effect: dev posture renders the real `Login` picker on /login (users list, hint prefill, bootstrap window when the users table is empty — Login.tsx needs **no change**); production behavior is byte-equivalent. The other arm (`!authed → /login`) is untouched.
- **R11 — Sign out renders only when it can work:** `authed && session.dev !== true`. Under the dev fallback it is replaced by the honest affordance that CAN work — a `Link` to `/login` ("Sign in") — which is what makes the picker *reachable* rather than merely servable (OQ4 records this reading; the gate's fix candidate names the picker render + the Sign out hiding; the link is the minimal honest completion). The who-line keeps its honest 'dev' label.
- **R12 — the full dev-posture cycle is honest and asserted:** dev fallback → /login renders picker (no bounce) → real login (`POST /api/auth/login`, cookie set) → session re-read serves the real user, `dev` absent → Sign out renders → fires `POST /api/auth/logout` + re-read → dev fallback again, Sign in link back. Assert with the fetch log (the acts fired), not render alone.
- **R13 — no pretend-auth, no invented states.** The client renders exactly the two server states (`dev:true` fallback / real user); it never synthesizes a "signed out" state the server did not serve, never blocks the dev identity from browsing (deny-by-default reads are the server's job and already hold), and never renders Sign out it cannot honor. The dev-fallback state is not a signed-in person; it is the absence of one with browsing rights.
- **R14 — tests, both postures.** `doubles.ts` gains a dev-fallback session double (`{authenticated:true, dev:true}` — none exists today; `signedIn`/`signedInAsOperator` are both real users). `shell.test.tsx` gains: picker-on-/login under dev (no bounce), Sign out ABSENT + Sign in link present under dev, the R12 cycle, and the production negatives kept green **unmodified where possible** (the :211 no-session redirect and the :362 Sign out test run under real sessions and should pass untouched — a modification there is a finding, not an update). Hazard named for evaluation: this is the exact "passes in jsdom, false in production" class the batch record warns on, IN the dev-login area where the batch already caught one instruction error — the evaluation must check the arm against the SERVED session shapes (auth_handlers.go), not against the doubles' own invention.
