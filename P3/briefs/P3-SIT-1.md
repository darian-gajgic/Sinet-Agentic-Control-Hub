## 2. Requirements (each with its S-ref)

- **R1 (S13.1 content pin; S13.2 type table; S07.8)** — `reviewSink.MintCandidate` takes the round-boundary snapshot BEFORE `ensure`, and THE task deliverable is ensured with dtype `code` iff `snapshotSHA != "" && d.Domain == verify.DomainSoftware`; otherwise `d.Type` (with today's `""` → `"text"`). The revision keeps `Files: {deliverable.md: d.Content}` (the companion), `SnapshotSHA`, and the platform ref. `EnsureDeliverable` stays idempotent (an existing row keeps its type). `skeleton.go` untouched.
- **R2 (S13.1, S13.2)** — `review.Store.Compare(id, oldN, newN)`: when `newRev.SnapshotSHA != ""` and `s.Tree != nil`, the TREE lane: surface `line-diff`; `Change` = the inventory from `Tree.TreeChanges(oldPin, newPin)` where `newPin` = revision newN's snapshot, `oldPin` = revision oldN's snapshot (oldN ≥ 1) or `Tree.TreeBase` (oldN = 0, `OldIsBase = true`); `Unified` = for each non-binary inventory row in path order, `gitDiff(row.Path, oldBlob, newBlob)` (a rename diffs `OldPath`'s old blob against `Path`'s new blob, header named by `Path`; an added file diffs against `""`, a deleted file to `""`), concatenated — bounded per R6. Binary rows contribute no text. `TreeBase` ok=false with oldN = 0 → `Change{AbsentReason: "no pre-task base is recorded for this work", Files: []}`, `Unified: ""` — an answer, not an error. `s.Tree == nil` on a repo-backed revision → today's companion diff with `Label` stating the tree source is not composed (no inventory). Content-pinned revisions: byte-identical to today; `Change` nil and absent from the wire.
- **R3 (S13.1 "any pair diffable on demand")** — `Store.Change(id, oldN, newN)` returns the inventory only (no blob reads), same pin resolution and absences as R2. Every pair oldN ≠ newN, oldN ≥ 0, newN ≥ 1 is answered.
- **R4 (S13.2, S15.3)** — `Store.CompareFile(id, oldN, newN, path)`: `Change.Files` = that one row, `Unified` = its diff bounded by `TreeFileDiffBytesCap`; a path the inventory does not cover → `ErrNotFound`.
- **R5 (S15.3, S13.2)** — `Store.RevisionFile(id, n, path)`: the tree blob at the revision's pin (via `TreeBlob`, at most `TreeFileBytesCap` bytes; `Size` = the full blob size); `Binary` by the git heuristic (a NUL byte within the first 8000 bytes) ⇒ `Content ""`; a path not in the tree resolves to the revision's own content object of that name (the companion report; hash-verified through the object dir); content-pinned revisions serve their objects the same way. `Pin` = snapshot sha or content hash. Unknown path, or a revision that does not exist → `ErrNotFound`.
- **R6 (S15.3 snapshot economy)** — bounds, each hit served honestly: whole-change `Unified` ≤ `TreeDiffBytesCap`, cut at a FILE boundary (the first file that would cross the cap and every later file are omitted; `Truncated = true`, `TruncationReason` names how many of N changed files the text holds and points at the per-file read); per-file `Unified` ≤ `TreeFileDiffBytesCap`, cut at the last hunk boundary that fits, else the last line boundary (the reason names the file's full diff size); file `Content` ≤ `TreeFileBytesCap`, cut at the last line boundary (the reason names the full size). The inventory is never truncated. A blob is never read past the cap it serves under (`TreeBlob` `limit`).
- **R7 (S13.3, FC-v1 §2)** — anchors on a repo-backed revision resolve against the tree: the file map the three consumers read (`AddComment`, `AddFindings`, `placeAll`/`filesAt`) is, for a revision with a snapshot pin, the tree blobs of exactly the paths the anchors name (per (revision, path), `limit = TreeFileBytesCap`; a path beyond the cap or absent degrades by the existing ladder) merged with the revision's content objects — bounded by the anchored paths, never by tree size; content-pinned revisions keep `RevisionFiles` as the map. `RevisionFiles`' exported behaviour is unchanged. `validateBirth`/`portAnchor`/`ParseFindingAnchor` unchanged. Revision 1's old side keeps `BaseContent`.
- **R8** — content-pinned lanes and composer definitions: no wire, behaviour or golden change.
- **R9 (S13.1 immutability)** — no migration; repo-backed derived from `snapshot_sha` on read; old rows serve the tree with their recorded dtype.
- **R10 (S15.2 additive, S15.3)** — `DeliverableDetail` gains `change *review.Change` (`json:"change,omitempty"`): for a repo-backed current revision, `Store.Change(current, current−1)`; absent for content-pinned; a nil tree source or a pin the store cannot resolve → `change.absent_reason` (the error LOGGED) and the detail still reads (the `revisionVerification` posture, §38 "absences are rendered").
