## 1. The seven questions, settled

**(1) What a checkpoint row holds and what the fork consumes.** Row = S02.4 (a) `usage_json`; (b) `session_substrate, session_id, message_index, cwd_key, transcript_path`; (c) `ledger_revision` (= `{"ledger_version":N,"sha256":…}` from `ledger.Store.CheckpointRef`, `internal/adapters/driver.go:347-353`); (d) `artifact_snapshot_ref` (= `project.Store.Snapshot` commit sha via the shell's `pseams.Snapshot`, `driver.go:339-345`, `shell.go:704`); (e) `model_id, invocation_fingerprint, tool_schema_version, prompt_schema_version`. The fork consumes `checkpoint_id` and `event_seq` ONLY, as event-detail bookkeeping (`recovery.go:725-736`). It ignores the snapshot ref, the ledger revision (which, via the ledger doc at that version, encodes the step position) and the session cursor. The step position is derivable today from the parent's `ledger_update` rows (v21 above) but nothing derives it.

**(2) The resume unit.** Step-granular: the first plan step NOT recorded complete, on the tree of the last completed step. Grounds: S05.3 — one fresh session per stage (execute-N), "a continued or resumed transcript is never the mechanism for crossing a stage boundary"; S06.6 — each step carries the "Done when" contract, the platform's unit of completion (`verbs.State(done_unverified)` at `skeleton.go:747-751`); S13.5 — snapshot commits "at stage/round boundaries". Message-granular resume (S-4 at msg 21) is rejected as the v0 rule because the Claude-lane engine cannot be re-entered mid-step across a dead process without (a) the engine's OWN session store still holding the session (the copy-aside is a harvest source, never re-loadable, S02.4 "engine transcripts are NEVER durable checkpoints"), (b) a full invocation re-supply, which exists only for parked asks (`ParkRecord`, `Driver.DriveResume`, S03.4), and (c) a continuation prompt no S-text ratifies. S02.5 step 5's "re-hydrate the engine where it still holds" is about ASKS. So: **k = the number of leading plan steps whose ledger item is `done_unverified` (or `verified`) AND carries a step-close snapshot as `evidence_ref`; the successor drives steps k+1..n on a worktree restored to item k's snapshot; k=0 restores to the attempt base.** A mid-step partial restarts its step from the start. Residual over-spend is bounded by one step, not one paid call — stated honestly; S02.4's "since the last paid call" bound is the cache-economics half at v0.
**Harvest of S-4 (FINISHED-DURING-OUTAGE at step granularity):** S-4's session DID end (`end_turn`; its 20 checkpoints exist; the tree at its end is on disk at fork time) and its output IS harvestable in principle (snapshot the tree at fork time as S-4's close; its deliverable text only matters for the FINAL step). It is NOT harvested by this packet: deciding that an `outcome=error` stage counts as done is exactly the carried stage-endings question (§72 last bullet; gate record line 147). Today `HarvestSource` is the B0 `NoHarvest` no-op at every wiring (`internal/recovery/seams.go:80-87`, CONVENTIONS §54), so no harvest fires on any real run; and run-level harvest→`completed` is the wrong shape for a multi-step leg anyway (it would complete a run with steps left). Recorded for the stage-endings packet: with this packet's step-close snapshot in place, that redesign's harvest becomes "mark S-k done with a fork-time snapshot as evidence" — one ledger write.

**(3) The worktree at fork.** Never re-driven as-is. New verb `project.Store.RestoreSnapshot(ctx, worktree, sha) (head, error)`: index + working tree made identical to `sha^{tree}` (tracked files restored, files absent in the target removed, untracked non-ignored residue cleaned under the platform excludes; ignored junk left alone — it was never in a snapshot), then committed FORWARD as a new platform snapshot on the run branch via the existing `Snapshot` path (no-change → HEAD unchanged, never `--allow-empty`). The branch only fast-forwards (S13.5; CONVENTIONS §23 "fast-forward, never --amend"; `AdvanceRunBranch` doc `workspace.go:222-227`), so the dead run's per-call snapshots — including the discarded partial — stay reachable as ancestors of HEAD: **nothing is lost.** What the restore discards from the WORKING TREE: the dead run's partial-step edits and untracked files (captured in its last per-call snapshot, `efa67b8269…` in the sitting world) plus any residue after that snapshot (captured nowhere — it was in no checkpoint, S02.4 bounds re-spend to "since the last paid call" and this residue is exactly that window).
