## 1. The gap, as it stands in the code today (every claim verified this session)

1. **The promise exists; the door does not.** GF4's landed disclosure says "Capturing the project's commands restores the full ladder from the next revision on" (`internal/verify/bootstrap.go:47`), and the pre-GF4 parked cards say "capture them for the project (its Commands), then retry" (operator record §F1). Nothing in the product can capture: `web/src/Projects.tsx:583` renders "no commands captured" (display only), and `/api/projects` has exactly three doors — GET list, GET detail, POST create — with "Re-scan on demand (S13.7), member management and deletion" recorded as deliberate absences (`internal/api/projects.go:22–28`).
2. **The only landed writers of `repo_registry_captures`** are `project.Onboard` (the scan's draft, v1), `project.Approve` (the owner's edited draft at the D10 onboarding card), and `project.Rescan` (Go verb only — no HTTP door; `internal/project/onboard.go:231`). Migration `0008_repo_registry.sql:69–71` itself anticipates this packet's writer: "the version bumps on every re-capture/re-scan/**edit** and stays traceable". Rows are immutable + never deleted (triggers, 0008:90–99); PK `(project_id, version)`.
3. **Re-scan cannot mint the card's commands.** `Rescan` → `Scan(e.StorePath, e.DefaultBranch)` reads repo content. In the F1 scenario the project is a fresh scaffold whose task never delivered — there is no Makefile/package.json at HEAD to scan. Only an owner-typed **direct write** can put commands into the capture. (This decides question 1 — see OQ1.)
4. **The consumption side is already done (GF4).** `projectSeams.CheckPackFor` resolves the pack per (domain, task) from the registry's **current** capture on every round (`internal/shell/project_seams.go:260–277`; `packFromCapture` → real `CheckPack` when any of build/test/lint is non-empty, `verify.BootstrapPack` otherwise, :412–441). A capture write therefore takes effect on the next verify round with **zero verify-side changes**: a parked pre-GF4 card's `retry` and a mid-drain capture both pick the new pack up. GF4's tests pin this (`internal/verify/bootstrap_gf4_test.go` — `TestGF4PostureRecomputedPerRevision` etc.; `internal/stage/bootstrap_gf4_test.go` — `TestGF4RetryOnPreGF4CardLandsInBootstrap`). GF5 must leave them byte-green.
5. **The verified-on interplay is landed semantics, unchanged by this packet:** the pack's `VerifiedOn` = the capture's own timestamp ("a suite is exactly as fresh as the scan it came from", project_seams.go:240–242), and `CheckPack.AuditStale` measures ⚙ `verification.check_audit_interval_days` from it (`internal/verify/v1.go:185–196`). A fresh capture from this door mints a fresh stamp — a NEW suite version with a new capture date, exactly what S13.7 "captured content is versioned" + S07.9 P-T06-1 describe. No change needed; a test states the fact (T6).
6. **No machine-readable bootstrap marker reaches any FE-consumed read.** `posture`/`posture_note`/`review_mandatory` live on the verdict EVENT row only (`internal/verify/record.go:92–94`) and on the receipt as prose (`internal/stage/surface.go:473–489`). `web/src/api.ts` has no posture member on any deliverable shape; the review surface receives the note as a comment whose non-positional anchor is the raw token `check-pack:absent`. GF6 cannot decide when to render the door except by string-matching prose or a machine token — the fragile jargon-coupling the RA-13 family and §38's ban-on-matching-text both condemn. The packet order assigns the wire fix here (question 5) — R9.
7. **The §40-B wall stands:** `internal/api` imports neither `internal/project` nor `internal/broker`; every registry mutation goes through a composition-root seam (`onboardDoor`, project_seams.go:131–171), refusals translated on sentinels (`onboardRefusal`, :177–188). The write door must ride the same shape.

## 2. Requirements (each with its S-ref)

- **R1 — the door: `POST /api/projects/{project}/commands`.** Body `{"commands": {"build"?, "test"?, "lint"?, "run"?, "preview"?}}` — the five S13.7 slots, **full-replacement semantics**: the submitted object becomes the capture's whole `commands` member; an omitted or empty slot is cleared. Response 200 (this API answers 200 for every act — projects.go's own no-201 rule): the updated `ProjectDetail` re-read through `visibleProjectRows` (the create door's "describe a project in exactly one way" precedent), a plain-words `detail` sentence, and the `cursor`. [S13.7; S15.2 additive family rules; operator record F1b]
- **R2 — the store verb: a new immutable capture version with everything else carried forward.** `internal/project` gains `EditCommands(ctx, projectID, by string, cmds Commands) (Capture, error)` (name the executor's): reads the entry's current capture, writes a NEW version via the versioned-capture machinery with `Conventions`, `DangerZones`, `ScanHash` and `Family` carried forward **byte-equal** and only `Commands` replaced — the exact `Rescan` family-carry-forward precedent (onboard.go:240–252), for the same reason: dropping the scan hash would make `DriftCheck` compare against nothing, and dropping conventions/zones would silently unset owner-approved content with no event behind it. [S13.7 "captured content is versioned"; migration 0008's "edit" comment]
- **R3 — owner-only, one-refusal discipline, active-only.** Only the owning user writes (D10 "their own object"; the `Approve`/`Activate` `ErrNotOwner` posture): a **visible member** gets an honest 403 naming the owner-only rule and the owner (they can already read `owner` on the detail); an unknown id and an **invisible** entry share the ONE `errNoSuchProject` 404 — same status, same body, no id echoed (§38 404-before-403; the `noSuchPin` discipline). The dev-posture identity is refused exactly as the create door refuses it (browsing is not filing, projects.go:576–585). A **pending** entry is refused with a sentence pointing at its real door — the onboarding approval card in the Inbox, where the draft (commands included) is editable (`OnboardApprove` with an edited draft) — because a second write path onto a pending draft is the double-mint shape projects.go's "three doors and no fourth" comment names. Visible-pending may be told honestly (the `ErrNotActive` precedent, `PinForIntake`). [S13.7 owner-attributed; S15.2 server-side authority]
- **R4 — validation at the boundary; never execution.** Per slot, after trim: single line (`\n`/`\r` refused), no NUL, valid UTF-8, rune cap via a structural constant (recommend `commandMaxRunes = 500`; the `cancelReasonMaxRunes` precedent, actions.go:47–59 — **no new ⚙**, S13.7/S18 ratify none; interim under the standing settings-tab directive). Refusals are 400s that name the violated rule and the slot. All-five-empty is **allowed**: it returns the project to the bootstrap posture, which is the honest recompute, not an error. **Nothing is executed, resolved, or dialed at capture time** — a captured command runs only later, inside the network-off C2 verification sandbox as `/bin/sh -lc <cmd>` (project_seams.go `packChecks`; S07.3 rule 1; S11), where the platform reads the exit status. No shell-safety allowlist: the owner already owns arbitrary code execution in their own repo (its Makefile is theirs), and a token filter here would be theater posing as a boundary. [S15.2; S07.3; S11]
- **R5 — retry-safe write (S15.2 "a phone retry can never double-fire").** A submission whose validated command set equals the current capture's commands byte-for-byte mints NO new version, appends NO event, and answers 200 with the current state and a detail sentence saying nothing changed — the create door's already-started precedent.
- **R6 — attribution + event.** The new version's `captured_by` = the caller; the write appends the existing `registry.captured` event (project.go `EventCaptured`) attributed to the caller — **no new event type** (naming is provisional pending S14, CONVENTIONS §7/§8). The audit record must distinguish an owner edit from a scan draft: recommend an additive, omitempty `origin` member on the capture event payload (`"edit"` here; existing callers unchanged → existing event bytes unchanged). If the §29/§32 conformance registry resists even an additive member, the executor records the distinguishing fact another honest way and says so. [S13.7 owner-attributed; 15.6]
- **R7 — version allocation is race-safe.** Today `Capture` reads `e.CaptureVersion` BEFORE opening its `WriteTx` (registry.go:231–246), so two concurrent writers race to the same `version+1` and the loser dies on the `(project_id, version)` PK as a 500-shaped constraint abort. The verb this packet adds must allocate the version **inside** the write transaction (re-read or `SELECT capture_version …` in-tx); fixing `Capture` itself for all callers is in scope if that is the simpler seat. A lost race surfaces as a retryable refusal or a clean second version — never a raw constraint error on the wire.
- **R8 — the seam shape.** `internal/api` gains a narrow surface (e.g. `ProjectCommandsSurface { SetCommands(ctx, caller, projectID string, c ProjectCommands) error }`) on `api.Config`, nil → 503 `not_wired` (the `onboardReady` precedent, projects.go:776–783). The composition root implements it in `internal/shell/project_seams.go` over the R2 store verb (the `onboardDoor` precedent) and wires it beside `Onboard:` (shell.go:987). Refusal translation on SENTINELS only (`ErrNotOwner`→403, `ErrNotFound`→the one 404, `ErrNotActive`→conflict, `ErrBadInput`→400) — never on message text (§38). The §40-B wall stays AST-clean: production `internal/api` still imports neither `internal/project` nor `internal/broker`.
- **R9 — the machine-readable posture member (the door-link's wire half).** The deliverable detail read (`internal/api/deliverables.go`, `DeliverableDetail`) gains an additive `verification` member for the **current** revision: `{"posture": "bootstrap", "review_mandatory": true}`, the whole member **absent** (raw-JSON key absence, the GF4 drain-F3c lesson) for the ordinary posture. Source: the revision's `verdict_ref` (= the `verify.round` event seq, `internal/review/review.go:153`) → that row's `posture`/`review_mandatory` payload members (record.go:92–94). Closed-vocabulary string + bool only — no note text (the plain-words note already reaches review comments, GF4 drain F2, and the receipt; closed-vocab structural fields are the §38-ruling-(b) exempt shape, so no new redaction edge). `web/src/api.ts` mirrors the member BY NAME (§41) — a type addition, no view change. GF6 then renders the door from `verification.posture === 'bootstrap'` + the row's `project_id`/task join, never from prose. [S07.8 A14 "the verdict card … names the bootstrap posture"; GF2's rule]
- **R10 — GF4 is load-bearing and untouched.** No change to `CheckPackFor`/`packFromCapture`/`internal/verify` bootstrap machinery beyond R9's read-side serving. The GF4 batteries (`internal/verify`, `internal/stage/bootstrap_gf4_test.go`) pass unmodified — they are the proof that a capture landed through this door is picked up per revision.
- **R11 — golden fixtures for GF6 (§42), with the battery owed.** The projects family currently has NO golden fixture (verified: no project body under `web/src/fixtures/api/`, no "project" in `apifixtures_test.go`). This packet lands the bodies GF6's doubles will import: the projects list, a project detail whose capture holds commands, the commands-write response, and a deliverable detail carrying the R9 bootstrap member — each seeded by **driving the real verbs** (the §42-B root-cause rule: a fixture is producer-minted, never author-imagined), fixed-clock, compare-only with the `SINET_WRITE_API_FIXTURES=1` regen path.
