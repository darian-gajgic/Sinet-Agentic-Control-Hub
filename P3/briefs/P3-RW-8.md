## §1 The defect — verified at this tree, mechanism end to end

Builder-found on the live world (STATE.md 2026-08-12), coordinator mechanism-verified, re-verified line by line at this grounding:

- **The durable onboarding ask declares NO answer vocabulary.** `onboardCard` (internal/stage/onboard.go:86-93) snapshots exactly `{kind:"onboard", project_id, owner, draft, issued_ts}`. The inbox derives a card's verbs from the snapshot's OWN declaration — `readCardShape` (internal/api/approvals.go:713-750) recognizes four families: `approval.actions`, top-level `choices` (the S07.7 verify shape), `decision.choices[].value` (the S06.7 intake shape, `[]Option{Label,Value}`, intake/cards.go:75-80 + taxonomy.go:20-23), and `delta.actions`. The onboard snapshot matches none → `Actions: nil` on a card served `answerable:true` (owner) — and the SPA, which renders buttons strictly from served `item.actions` (web/src/Inbox.tsx:1182, 1282-1305), renders the honest dead end: *"this card declares no answer verbs, so there is nothing here to press"* (Inbox.tsx:1221-1227). No surface can approve an onboarding; D10's owner approval (S13.7) is reachable only by hand-crafted POST.
- **The server-side answer path works** (builder-proven by raw POST): `POST /api/asks/{ask}/answer` and `POST /api/approvals/ask:{ask}/answer` both route an `onboard:`-prefixed ask through the stage Surface to `AnswerOnboarding` (internal/stage/surface.go:145-153; internal/api/approvals.go:1049-1068, 1073-1137 — the pin, scope and tier gate live in `answerAsk`; the ask vocabulary does not). `AnswerOnboarding` accepts `{approve: bool, draft?: json}` (onboard.go:95-99, 208-281).
- **THE LOAD-BEARING SUBTLETY the one-line cut ("declare the vocabulary; the SPA renders it for free") misses:** rendering is free, FIRING is not. The SPA composes the answer body per the snapshot's family (`answerEnvelope`, Inbox.tsx:1407-1415; `composeAnswer`, Inbox.tsx:1528-1549): the `decision` family composes `{choice:"<value>", criteria?}`. Go's `json.Unmarshal` ignores unknown keys, so `{choice:"approve"}` unmarshals into `onboardAnswer` as `approve=false` → refused by onboard.go:239-241. Declaring the vocabulary WITHOUT teaching `AnswerOnboarding` the declared family's envelope produces a rendered button that always fails. The packet is card + answer-envelope, one producer, one commit.
- **Reject semantics (settled by read, not assumption):** decline is NOT implemented. `AnswerOnboarding` refuses `approve:false` outright — *"onboarding answer must approve (edit-and-approve is the only verb at v0)"* (onboard.go:239-241) — and S13.7 defines only "the owner approves the draft (D10)"; no decline exists anywhere in the spec. S15.2's family-level "approve / deny / answer / re-plan" is the mapping VOCABULARY, not a per-card guarantee (the `ApprovalItem.Actions` doc says exactly this, approvals.go:164-167). So the honest card offers ONE verb: **approve**. The exit that DOES exist and is verified: task cancel — `CancelTask` (internal/stage/cancel.go:197-241) finalizes the parked run with-card and `closeOpenAsksTx` closes the open ask as `cancelled` in the SAME transaction (cancel.go:288-304, :371); the pending `repo_registry` entry persists (cancel never touches internal/project) — pre-existing, out of scope, and the card must not claim otherwise.
- **Wording defect:** `onboardStartedDetail` (internal/api/projects.go:242-244) tells the OPERATOR "The approval card appears in /api/approvals" — an API path in human prose. The surface's operator name is **Inbox** (web/src/routes.ts:71 — title `Inbox`, path `/inbox`; P3/design/product-map.md:22, :52, :89-90 "Inbox (one queue for everything needing a human)"). The machine-readable reference already rides the structured `ask_ref` field (`ProjectStarted`, projects.go:218-224) — prose and reference are cleanly split today; only the prose is wrong. No test pins the current sentence (grep-verified).
- **Which family, decided by the consumer's real behavior (web/src read REFERENCE-ONLY):** the `decision` family is the only non-plan family that BOTH renders and composes. It renders `DecisionCard` — summary + "What this is about" bullets + the 13.5 `Help` block (Inbox.tsx:950-959, 978-996) — derives labeled-value actions, and composes `{choice}`. The verify-style top-level `choices: []string` renders buttons but composes NOTHING: `answerEnvelope` does not recognize it → `unknown` → `composeAnswer` returns null → "not sent" (Inbox.tsx:1414, 1546-1547). **Side-finding for the coordinator, NOT this packet's scope:** that gap means S07.7 verify-escalation cards appear un-fireable from the SPA today for the same reason this packet exists.
- **Ask-snapshot discipline / production compatibility (settled):** the platform ask row is "authoritative from the moment observed" (Spec S02.2 — the doctrine internal/verify/escalate.go:234 cites) and its snapshot is the resume input (Spec S02.5 recovery step 5 "Asks reconcile", drafts line 79). The ONLY writer of this snapshot is `dispatchOnboard`'s upsert, which re-marshals on every dispatch (`ON CONFLICT (ask_id) DO UPDATE SET … snapshot = excluded.snapshot`, onboard.go:183-197, incl. the RW-6 R11 run rebind) — so every NEW or re-dispatched onboarding carries the vocabulary with no re-issue mechanism needed. A pre-upgrade OPEN ask keeps its old-shape snapshot: `readCardShape` yields nil actions → it renders exactly today's honest verb-less state, stays answerable via `{approve:true}`, and its read-derived pin (`gates.CanonicalHash` at serve time, approvals.go:696, 1101) stays self-consistent — degraded but never broken, and never a crash. The dev world is wiped by reseed (the open `onboard:garden-guide` is reborn with vocabulary); no production deployment carries open onboardings across this upgrade. **No migration, no re-issue door — a startup snapshot-rewrite would be new machinery for a world-class that does not exist.**
- **CARD vs READ (settled):** the CARD. ## §2 Requirements

- **R2 (the fire path; S15.2 additive-first).** `AnswerOnboarding` accepts the envelope its declared family composes: an answer carrying `choice` must name a declared value (`"approve"` → approve; any other non-empty `choice` → refused with an error NAMING the declared vocabulary; `criteria`, which the SPA's `CriteriaPicker` may append, is tolerated and ignored).
