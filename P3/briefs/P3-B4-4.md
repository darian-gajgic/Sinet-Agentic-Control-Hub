### C — Ports: netns probing + `sinet-portpool` consumption

- **R8.** **Netns port probing — config is never trusted** (S13.8 "the platform probes the netns for listening ports rather than trusting config"): the dev server binds 0.0.0.0 inside the preview sandbox's netns; the platform discovers listening ports by parsing the sandboxed process tree's `/proc/<pid>/net/tcp` + `tcp6` LISTEN rows (the process's own netns view — no nsenter, no privilege). Pure parser unit-tested on fixture proc files; a live probe test (sanctioned-skip when caps absent, §12) starts a listener inside a composed sandbox and asserts the probe sees it. **Multi-port → picker data**: the probe result is a typed list; when >1 port listens, the preview state carries the picker data (port + best-effort label) for S15 (B6); single port auto-selects.
- **R9.** **Portpool consumption — file-stub OK dev-mode** (S13.8 "the port comes from `sinet-portpool` [XREF:S01]"; S01.2 `sinet-portpool.service`, loopback only; acceptance headline): a port-pool **allocator over a fixed configured host-port range** backed by file-based reservations (the "file-stub" — `P3/STATE.md` B2: "portpool file-only — stub mode"), giving each live preview its host-side public port (the Caddy upstream / socket-unit port). Allocate on launch, release on teardown; crash-orphaned reservations are reclaimable (stale-owner detection — executor discretion, tested). The range is **structural config** (code default + composition-root override; NO ⚙ key exists and none may be invented — §8 reading 3): a SMALL fixed range is load-bearing for the §8-1 pre-installed-static-units bring-up shape. Dev-mode and tests consume the allocator **in-process** — no daemon required (the headline's "file-stub OK dev-mode").
- **R10.** **The `portpool` daemon mode is FILLED, leaving the reserved table** (S01.5 multi-call; `internal/cli/cli.go:71` reserved `"portpool"`; the cli.go comment records the precedent — "The broker mode is implemented at B1-3 and left the table", i.e. a daemon mode lands at its consuming packet; S13.8 names the port-pool daemon as one of the only two pieces of novel preview code, the other being S15's UI): `sinet portpool` serves the same allocator on **loopback/UDS only** (S01.1 invariant — 127.0.0.1 or unix socket; the S01.4 IPC-transport choice is P3's within that bound), so the generated `sinet-portpool.service` (`internal/units/units.go:268`, `ExecStart=%s portpool` — already renders, untouched) has a working mode behind it. Thin: serve/allocate/release/list over the file-backed core; a loopback-only self-assert at start (the P-T13-2 posture). The unit stays generated-never-installed; nothing starts it in tests (the daemon is exercised in-process/via its serve loop on a test socket).
- **R11.** **Static server lane** (S13.8 `index.html` → static server): platform-served — stdlib `http.FileServer` over the read-only revision checkout, bound **127.0.0.1:\<allocated pool port\>** (loopback only, P-T13-2; the ONE preview lane that runs host-side platform code rather than a sandboxed toolchain — it executes nothing and serves read-only bytes; state it in a doc comment).
