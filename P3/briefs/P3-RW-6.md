## §2 Requirements

### Group A — the fork must supersede (defect 1)

- **R1 (S02.5 steps 2–4; S02.3).** `dispatchIntake` passes the fork's identity into the pipeline: the intake advance entry consumed by dispatch takes BOTH the task id and the dispatched run id (new method or added parameter on `intake.Pipeline` — the pipeline owns the rebind; the skeleton only hands over `r.ID`). The answer paths (`Answer`/`applyApprovalAnswer` → `advanceLoaded`) keep driving `st.RunID` — correct post-rebind by construction.
- **R2 (S02.5 step 2 "supersede"; CONVENTIONS §13).** On dispatch with `runID != st.RunID`, the pipeline REBINDS: `st.RunID = runID`, persisted as ONE `intake.state` event appended on the FORK's run at the FORK's current generation (the existing `appendStateTx`, state.go:252-271, already reads the generation in-tx). - **R3 (lineage guard; S02.5 step 3, migration 0002).** The rebind is guarded by `runs.parent_run_id` lineage: walking the dispatched run's `ParentRunID` chain (each hop a real row) must reach `st.RunID`; the dispatched run's `TaskID` must equal `st.TaskID`. A same-id dispatch (`runID == st.RunID`) is a no-op. A run failing the guard is refused loudly (error → the dispatch crash path) — no rebind onto an unrelated run, ever. NOTE the multi-hop case is REAL: if fork g1 crashed before its own rebind committed, `st.RunID` still names the ORIGINAL while the dispatched run is `….g1.g2` (the live-world lineage above is exactly this).
- **R4 (S06.1 gates wait).** If the rebound state carries `st.OpenAskID != ""` (defensive: a fork dispatched over a state that says a gate is open), the fork must land PARKED on that gate (running→parked in the dispatch leg), never left running-idle for the ladder to reap.

Post-rebind, `advanceLoaded`'s Hold (pipeline.go:350) and `approve`'s Beat (answer.go:544) target the FORK at ITS generation. The packet's acceptance test asserts the parent-side renewal no-ops (T-A1).
- **R6 (S02.3 one-WriteTx discipline; CONVENTIONS §8).** Every new transition introduced by this packet rides `run.Store.Transition(Tx)` — state update + event append in ONE WriteTx at the correct generation. No hand-rolled UPDATE of `runs.state` anywhere.

## §6 Acceptance headline → checklist

**Headline: a crashed intake run's fork takes over and finishes the interview (the t-80eff shape heals end-to-end); no dispatch outcome can strand a claimed run without a corpse; no production run class is fork-bait by its id shape; ladder-terminal runs release their queue rows.**

1. [ ] Mid-interview crash → ladder fork → the fork's dispatch REBINDS state (one `intake.state` event on the fork at its generation) and issues the NEXT interview card with the continuing ask id `intake:<task>:<n+1>` — no ErrNotRunning, no re-fork, no tombstone.
2. [ ] Answering that card resumes and completes the interview through approval on the FORK; execution launches; the fork's run completes and settles.
3. [ ] Answered slots from BEFORE the crash survive — no answered question is re-asked; prior answered ask rows stay answered.
4. [ ] Post-approval crash shape: the fork completes ITSELF (never the parent) via `finishIntake` and launches execute.
5. [ ] Lineage guard: a non-descendant run id is refused (no rebind, loud crash path); same-id dispatch is a no-op.
6. [ ] Fence: the parent's stale keeper renews nothing — `RenewLeaseTx(parent, oldGen)` no-ops; the fork's Hold/Beat land at the fork's generation.
7. [ ] Fork-reachable planner/critic/router/utility/spot-check/tie-break calls carry the fork's run id (captured via seams) — no `taskID+".intake"` composition on a forked run's phase work.
8. [ ] Onboard: a crashed-then-forked onboarding run re-issues its ask bound to the FORK; the owner's approval activates the entry and completes the FORK atomically.
9. [ ] Execute fork keeps its project workspace lane (`WorkspaceCwd` answers for `….execute.g1`).
10. [ ] Unroutable Dispatch → the run is `crashed` with the cause in its event detail, in one tx — never left `claimed`; the (user,lane) slot frees immediately.
11. [ ] A crashed roleless run FINALIZES (reason named in the detail) on the next ladder pass — no `.g1` successor is ever created for it; `.direct` behavior unchanged.
12. [ ] Deadman: a sweep during a healthy probe leaves the canary alone (ALIVE); an orphaned canary is crashed+finalized within one pass-pair — no roleless fork chain, no queue row, ever.
13. [ ] Queue rows of runs in {completed, crashed, finalized, tombstoned, died-at-gate} settle to `done` on the next claim pass (incl. rows predating the fix — the live-world 16-row shape drains); `parked` open-gate rows and live claims are untouched.

## §9 Open questions (genuine design forks — the executor decides at the named default unless the coordinator overrides)

- **OQ1 — rebind mechanics + guard shape.** Default (grounded): a pipeline-owned dispatch entry (`AdvanceDispatched(ctx, taskID, runID)` or equivalent) performing guard→rebind→advance; the guard walks `parent_run_id` (R3). Alternative: rebind inside `LoadState` keyed by "latest non-superseded run of the task" — REJECTED at grounding: it moves supersession policy into a read path and unguards it. Second limb: should the rebind ALSO re-point the OPEN ask row's run_id (the R4 case)? Default: yes, in the same tx as the rebind event — cheap, keeps `asks.run_id` honest for recovery's step-5 join (recovery.go:730-734, which excludes asks on terminal runs).
- **OQ2 — where queue settlement lives.** Default (grounded): the scheduler's level-triggered claim-pass reconcile (R17) — kubelet-shaped, self-healing for pre-existing leaks, keeps the queue family single-owner (S10.7), zero new cross-package seams. Alternative: settle inside the ladder's bound-decision tx via an injected seam (atomic with the terminal, but adds a recovery→queue seam recovery has never had, and STILL needs the sweep for pre-existing leaked rows). Both are honest; do not implement both write paths for the same row class unless a test demonstrates a window that the sweep alone leaves misleading on a surface.
- **OQ3 — the deadman remedy choice.** Default (grounded): R15's structural NoFork-by-routability (finalize, never fork) — S02.5's fork exists to save paid work and a $0 momentary probe has none; S14.4 has the canary self-terminate; retention's "a PLATFORM-scope run mints no summary" is the same doctrine. A routable/no-op skeleton role was REJECTED at grounding: it would make a probe's fork dispatch and "succeed", fabricating a recovery that proves nothing, and would push watchdog semantics into the skeleton. The R16 Beat is an optional extra (keeps healthy probes out of the lease-dead statistic); take it only if it stays inside the §31 wall untouched.
- **OQ4 — does defect 1's fix generalize to other baked-RunID classes?** Sweep verdict (grounded, §1): intake is the ONLY class whose FSM resume is broken by a baked RunID; onboard has the ask-rebind tear (R11); execute has the workspace-gate miss (R12); verify/compose/direct are clean. The GENERAL rule to land as a comment convention (extending §16): "a run id is composed exactly once, at birth; every later consumer reads the run's CURRENT identity from state, never re-derives it from the task id". If A/B splits, R11+R12 stay in A.
- **OQ5 — one fork-aware suffix matcher.** Three exist: `runRole`'s strip loop (skeleton.go:218-235), `metering.stripForkSuffix` (ledger.go:236+), and project_seams' raw HasSuffix (wrong). Default: export ONE helper (natural home: `internal/metering` already exports the RunSuffix constants that `internal/stage` aliases — extend that seam; `internal/shell` imports both) and consume it at all three sites; do NOT churn `runRole`'s internals beyond delegation if the diff stays small. A fourth private copy is a finding.
- **OQ6 — receipt rule for swept rows** (R18): if `MaterializeTx` semantics fight the tombstoned/finalized case, the honest fallback is settle-queue-only + a logged deviation; never invent a receipt (D4).
