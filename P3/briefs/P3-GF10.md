## 1. The defect, precisely (code + walk-world DB facts, all verified this session)

The chain has five links; every one is at HEAD and none is bootstrap-conditional:

1. **The drain rides the verify run, and the mint stamps it.** `Skeleton.verifyInput`
   (`internal/stage/skeleton.go:1076-1091`) builds `verify.Deliverable{RunID: runID}` where
   `runID` is the VERIFY run (`<task>.verify`, or its recovery-fork lineage) — deliberately: "the
   drain's events, judge assemblies and checkpoints ride THIS run … its consumption is the
   verification tax (Spec S07.11)". `reviewSink.MintCandidate`
   (`internal/stage/review_sink.go:94-133`) then mints with `RunID: d.RunID` — so
   `deliverable_revisions.run_id` names the verify run for EVERY drain-minted revision, every
   round (`internal/verify/pipeline.go:405-414` mints inside the round loop; the resume path
   re-enters idempotently). The comment at `executeRunID` (`skeleton.go:279-295`) states it
   outright: the S13 revision row "is minted later, by the verify leg itself".
2. **Attribution resolves strictly through the minting run.** `acceptProvenance`
   (`internal/api/accept.go:313-342`): model + lane from the latest `routing.decided` payload of
   `rev.RunID`; engine from `engine_sessions.substrate WHERE run_id = rev.RunID`; empty model or
   engine ⇒ `Absent` ⇒ trailers unrendered.
3. **A verify run never has a routing decision.** `routing.decided` is emitted ONLY by
   `dispatchExecute` (`skeleton.go:656-665`; `emitRoutingDecided`, `router.go:198-227`), and the
   LN-9 `SetDecidedLane` stamp is "Deliberately on the EXECUTE dispatch only" (`skeleton.go:675`).
   So `p.Model` is ALWAYS empty when resolving a verify run ⇒ `Absent` fires unconditionally.
4. **The push arm closes on absent provenance.** `acceptable()` (`internal/api/accept.go:261-281`):
   a revision with `SnapshotSHA != ""` and `prov.Absent != ""` is `acceptable:false` with the
   Absent sentence as the reason; `handleAccept` 400s on `!card.Acceptable` (line 470-473); the
   accept door (`internal/api/deliverables.go:394-420`) serves the same verdict (it asks
   `acceptable()`); the FE withholds the form on `card.acceptable === false`
   (`web/src/Deliverable.tsx:2964-2985`).
5. **The truthful facts exist — one run over.** Walk-world DB, read this session:
   - `deliverable_revisions`: `dlv-t-7bc2336ad63fc226 | n=1 | run_id=t-7bc2336ad63fc226.verify |
     attempt_ref=…verify#round-1 | pin_kind=content | snapshot_sha=61015dd7c3c5…` (snapshot SET ⇒
     the PUSH arm — see the pin_kind note below).
   - `run_events routing.decided`: exactly one row, on `t-7bc2336ad63fc226.execute` —
     `{"model":"claude-sonnet-5","lane":"anthropic","generalist":true,…}`.
   - `runs`: the execute run row carries `lane=anthropic substrate=claude-cli` (the LN-9 decided
     stamp); `engine_sessions` holds substrate rows for intake, execute AND verify (all
     `claude-cli`).

**The absence sentence itself overclaims.** The verify run DOES record an engine substrate
(`engine_sessions` row `cfcaf979-… substrate=claude-cli`); what it lacks is only the settled
routing decision (the model). The served sentence — "records no engine substrate or routing
decision" — asserts an absence the database contradicts. The corrected flow must never claim a
fact absent that is recorded (R4).

**pin_kind is not the arm selector — do not "fix" it.** `pin_kind` reports the content-pin KIND
(`content` for Files, `objects` for binaries — `internal/review/store.go:221-224`) and is
independent of `snapshot_sha`; a repo-backed revision is `pin_kind:"content"` AND on the push arm.
The walker's card is consistent; no schema change belongs here.

**The wire already carries the withheld state as data.** `AcceptCard.Acceptable` + `.Reason` are
served (the B6-2A D9 discipline); the door serves the same pair; the FE has a
`data-not-acceptable` reason branch (`Deliverable.tsx:2981-2985`, present at the walk commit) and
renders the door reason as muted micro-copy (`:2943`). The walker — signed in as the owner
(`me = session.user_id = "darian"` = the deliverable owner) — still experienced the why as absent
from the card: the page header promises "accept it below" unconditionally, the Accept section's
plain copy promises the act ("When this work is right, accepting it makes it the official
version…"), the "Accept this work…" button renders regardless of acceptability, and the card's own
consent copy ("You are accepting revision 1 …") is unconditional. The withheld state is footnote
text under promise copy. GF10 owns the WIRE half (accuracy + completeness, R4/R5); GF9 owns
rendering it as the card's primary state.

## 2. Bootstrap-specific? NO — every drain-minted revision has this hole

- Structurally: links 1-3 hold for every launch-domain task deliverable, bootstrap or not, first
  mint and every V2-REVISE re-mint. There is no posture branch anywhere in the chain. A
  fully-commanded project's first deliverable walks into the same wall.
- Why it was never hit before: (a) the API test fixture `mkRun`
  (`internal/api/deliverables_test.go:208-227`) seeds `routing.decided` AND the engine session
  onto the SAME single run the revision is minted with — a one-run shape the production pipeline
  never produces (production: mint stamps `<task>.verify`, routing lives on `<task>.execute`); the
  push arm was only ever green against that fixture. (b) The only journeys that reached a real
  accept before WALK-F1 were pinned-arm (the `.sinet-rewalk-a` content deliverable — RW-17's arm,
  which is acceptable WITHOUT trailers because no commit is made). WALK-F1 errand 5 is the first
  time a real pipeline-minted, repo-backed revision met the accept door. The bootstrap posture is
  incidental: it is what put a fresh world's first deliverable there.
- Rework rounds: same hole (mint site is inside the round loop, same `d.RunID`). Note for R2's
  fill rule: rework content is regenerated by revise sessions that RIDE the verify run but
  dispatch on the task's recorded EXECUTE selection — `engineRevise` reads
  `st.Routing.Model/Lane/WindowTokens` (`internal/stage/engines.go:675-694`) — so the run whose
  settled selection produced every round's content is the task's execute run, for revision 1
  literally and for rework revisions by construction.

## 3. The design cut (the minimal seam)

**The revision carries the producing run's id, filled at mint; the accept resolves attribution
through it.** Not a copy of model/lane/substrate strings into the revision row — that would be a
side store of what the log already records (the derive-from-log rule, stated in this same file at
`mergeCardDurability`), and S08.8's own pattern is "version→outcome is a JOIN": the revision gains
the missing JOIN KEY, and `routing.decided` + `engine_sessions` remain the only attribution
stores.

Why mint-time recording, not accept-time derivation: which attempt produced revision N is a
per-revision fact fixed when the content is frozen; deriving it at read time re-walks lineage that
can advance (recovery forks) and would plant a second copy of the P3-RW-6 R12 lineage rule inside
`internal/api`. The mint site already lives in `internal/stage`, which owns `executeRunID`.

What must NOT move: `verify.Deliverable.RunID` and the minted `run_id`/`attempt_ref` stay the
VERIFY run — the drain's events, checkpoints, judge assemblies and the verification tax ride it
(S07.11), and S13.1's minting run/attempt ref members remain what they are. The seam is a NEW
member beside them.

- **R7 (never bypassed).** Forbidden landings, by name: a placeholder/default co-author; a
