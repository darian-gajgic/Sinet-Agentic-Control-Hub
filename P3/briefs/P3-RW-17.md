## 1. The symptom (blind-walk world, read-only evidence)

World `~/.sinet-rewalk-a` (STOPPED), task `t-bcd55c1619288004` "My photography website", owner alice, kanban `done`:

- Intake: `"family":"content","family_source":"classifier"` — so the run took the content-pin lane.
- Deliverable `dlv-t-bcd55c1619288004`: `dtype=markdown`, `project_id=''`, `current_revision=2`, `state=in-review`.
- Both revisions: `pin_kind=content`, `snapshot_sha NULL`, `content_sha256` filled, verdict refs recorded (verified SHIP).
- The wire: `GET /api/deliverables/{id}/accept-card` → `acceptable:false`, reason `"revision 2 is not repo-backed: it pins content but no snapshot commit, and an accept pushes a commit (S13.1/S13.6)"`.

The owner's Accept — V3, the journey's final press — is **structurally refused for every content-family task**, because content tasks have no project repo and the wire's precondition (`internal/api/accept.go`, `acceptable()`, lines 225–239) demands `rev.SnapshotSHA != ""` and `d.ProjectID != ""` for **all** deliverables.

## 2. The ruling: the spec DEFINES acceptance for payload-pinned deliverables — today's refusal is a DEFECT

The corpus answers in two layers, and both layers decide against the refusal.

**The accept decision is defined universally, with no pin-kind or repo qualifier:**

- Feature list 5.8 (outranks the spec, S00.2 precedence): *"The requester accepts or rejects; nothing self-approves into the world."*
- S07.1: V3 = *"the requester accepts or rejects (5.8)"* — a mandatory layer of the pipeline that ran on this very deliverable. S07.8: *"every other tier requires explicit accept (5.8)"* — the zero-interaction band relaxes only blocking-ness, never the existence of the act.
- D10 / feature list: *"Everyone approves their own objects — specs, plans, permissions, **deliverables**…"*
- S13.1: the deliverable state machine `in-review / accepted / superseded` is schema for **every** deliverable; and S13.1's own content-pin vocabulary covers non-repo types explicitly: *"A revision pins its content immutably: repo-backed types pin a snapshot-commit sha (S13.5); binary types pin content-addressed object-dir hashes (S13.2)."* **The payload hash IS the durable pin** — nothing needs inventing to record what was accepted.
- S13.1 again: automation definitions *"ride the same machinery"* and are approved by their owner as deliverables with **no outward push anywhere in their flow** (S08.6 approval-as-diff) — the corpus already contains a deliverable class whose acceptance is the S13.1 state transition, not a push. `review.Store.Accept`'s supersession logic exists for exactly that class.

**The S13.6 commit-push ceremony is the outward arm for repo-targeted work, by its own text:** every numbered step is defined over *"current project HEAD"*, *"run branch"*, *"protected ref"*, and its risk-tier parenthesis says why it is High: *"(risk tier High — outward push)"*. Feature list 6.3 names the landing target as *"the project's git repository **or document store**"* and S13.7 resolves the document store to the same per-project git repo. A deliverable with **no project at all** (the schema sanctions it: migration 0007, `project_id TEXT NOT NULL DEFAULT ''`; S06 registry match is best-effort) has no repo, no protected ref, and no push — so for it the accept is what S13.1 defines: the owner's decision moving the deliverable to `accepted`, recorded durably against the revision's immutable content pin, audit-trailed in the event log (`deliverable.accepted`, accepted_by).

Refusing the act therefore contradicts 5.8, D10, S07.8 and S13.1 simultaneously. **Defect confirmed; requirements and red tests below.** (What stays genuinely open — the doc-store *landing* for content revisions in projects that do have a repo — is OQ-B, scoped out honestly, not silently invented.)

## 3. How the seeded demo world's accepted d-notes happened (seed-direct, and it proves the point)

`internal/api/apifixtures_test.go` (the world behind B6-clickthrough.sh's demo seed): `d-notes` is inserted with `pin_kind='content'` revisions (lines 326–341) and then accepted by driving **the state verb directly** — `fixtureReview(t, b).Accept(ctx, "d-notes", "alice")` (line ~1298, commented *"A REAL deliverable accept through review.Accept"*). It never passes the wire's `acceptable()` gate or `internal/accept.Accepter.Accept`.

So the seeded accepts are **seed-direct through `review.Store.Accept`** — which has **no repo requirement at all** (`internal/review/accept.go`: state guard → supersession by subject_ref → state flip → owner-attributed `deliverable.accepted` event, idempotent on replay). The durable half of acceptance for a payload-pinned deliverable already exists and is exercised; only the wire refuses to reach it.

## 5. Requirements

- **R1 (5.8/D10/S07.8/S13.1).** An in-review deliverable with a minted revision is acceptable by its owner on the wire regardless of pin kind. `acceptable()` may refuse only for: not wired, not in-review, no minted revision, or repo-arm-specific facts (below). Pin kind is never a refusal.
- **R2 (S13.1 pin vocabulary; S15.2).** The pinned-arm accept records: the state transition via `review.Store.Accept` (supersession included), the `deliverable.accepted` event with `accepted_by`, and the act stays pinned to the card's `payload_hash` (which already covers `{deliverable, revision, content_pin, trailers}` — `checkAcceptPin` unchanged). Recommended cheap honesty: add `content_pin` to the event payload (derivable either way; not load-bearing).
- **R3 (one door; §24 walls).** The pinned arm executes inside `internal/accept` (branch in `Accepter.Accept` on `rev.SnapshotSHA == ""`, or a sibling method — builder's choice); `internal/api` keeps calling only the accept package. The pinned arm fires **no broker push, no class-A effect, no project mutation** — a DB state flip plus its event row is not an outward effect (S02.7 journals outward effects; nothing outward happens).
- **R4 (honesty per arm).** Card `Reason`/`TierStatement` state what WILL happen: push arm = today's text; pinned arm = "records your decision; the revision's immutable content pin is the durable record; nothing is pushed". Provenance-absent (`prov.Absent`) refuses **only the push arm** — the pinned arm renders no permanent commit trailers, so absent trailer facts must not close the act. `ProtectedRef` stays empty/absent on the pinned card.
- **R5 (retry-safety parity, §39 order).** Read-back of an already-accepted pinned deliverable returns 200 `applied:false` with empty `commit`/`effect_id`; `review.Store.Accept`'s state guard remains the structural backstop. Stale payload_hash → 409 with the fresh card, both arms.
- **R6 (S13.1/S13.9).** Supersession by `subject_ref` works through the pinned arm (review.Accept already does it). Sibling-accept freshness fires only when `d.ProjectID != ""` (project-scoped by definition; a projectless accept has no siblings to route).
- **R7 (regression).** The repo-backed arm is byte-identical: the whole existing acceptapi/accept/broker suite stays green, including `TestP_T12_1_ProtectedRefRefusal` and `TestAcceptCardWithoutProvenanceRendersNoTrailers`.
- **R8 (rider, recommended in-scope — see OQ-D).** `floor_reasons` (recorded in every `intake.state` payload; S06 Stage-0 record: "stakes tier + floor reasons"; feature list 13.5 "approvals explain themselves"; operator settings-tab directive) is served on at least one landed owner read — recommended: a small triage block `{family, family_source, tier, floor_tier, floor_reasons}` on `TaskDetail` (`internal/api/reads.go`, which already parses latest `intake.state`). One round-trip test.

**Named sub-choice (not silent):** the pinned arm keeps the full High-tier ceremony — payload-hash echo + PIN step-up — for accept-family uniformity, even though S13.6's High derives from the push. Conservative direction, contradicts nothing; relaxing later is an operator-visible change. Builder keeps `StepUpRequired: true` on both arms.
