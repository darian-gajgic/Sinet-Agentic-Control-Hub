### B — S13.6 Accept: one High-tier action through the effect journal (class-A)

- **R4.** **Applies-cleanly gate** (S13.6 step 1; S02.8 sibling-accept): before any push, the candidate revision (the minted revision's snapshot commit, B4-2 `refs/sinet/deliverable/<id>/rev-<n>`) is applied onto **current project HEAD on a throwaway ref** — a **depth-1 merge queue**; a second in-flight accept validates against **HEAD-plus-first** (S13.6 verbatim). This rides B4-2's **utility checkouts** (`project.Store.AddUtilityCheckout`/`ReleaseUtilityCheckout`, locked, never auto-deleted dirty — §23/R22) for accept staging, plus a NEW applies-cleanly/merge verb on `internal/project` riding the hermetic per-invocation git core (§23). A collision surfaces as a reviewable **merge card** with exactly three options — **agent-auto-resolve** (a bounded rework, S07 seam) / **resolve manually** / **abort to a new attempt** — NEVER a silent overwrite (S1.11 verbatim; S02.8).
- **R5.** **One clean attributed commit** (S13.6 step 2): the platform **squashes** the run branch's snapshot commits (base→candidate) into ONE commit whose tree is the accepted revision's, placed on current HEAD. Author = committer = the **accepting user**, set **per-invocation** (`GIT_AUTHOR_*`/`GIT_COMMITTER_*` env or `-c` — the §23 hermetic identity rule; **no global/host git config ever**). Committer email is the **ID-based noreply form** (`project.noreplyEmail`, survives renames) or a connected address from the per-user store. **Conventional-Commit subject**; body carries the task/session link as provenance. The squash is done **by the platform, never by a GitHub UI** (the squash-authorship hazard is structurally avoided, S13.6 step 2). No `--amend` anywhere (§23 tripwire holds — the accept commit is a fresh commit on HEAD, not a rewrite of the run branch).
- **R6.** **Deterministic attribution trailers** displayed on the card **before** accept (the VS Code mis-attribution lesson, S13.6 step 3): `Co-Authored-By: <engine> <model> <vendor-noreply>` (GitHub renders it) + `Assisted-by: <engine> (<model>) via Sinet` (machine-parseable). The trailer **template** is a **structural string constant** (§8 reading 2 — S18 ratifies no trailer key; not a ⚙ key; the `sseBatchSize` precedent, flagged to the B4 gate under the settings-tab directive); the **rendered trailers** are pinned in the effect payload at approval (deterministic, audit-trailed via the journal, displayed pre-accept). Never per-run improvisation.
- **R7.** **Accept rides the effect journal as a class-A effect** (S13.6; S02.7 — `git push --force-with-lease` is S02.7's OWN natively-idempotent class-A exemplar, already `gates.ClassA` in `internal/gates/effects.go`): the flow is `Journal.Propose` (ClassA; payload = the CAS **expect-sha** + the candidate **revision pin** + the **rendered trailers**; normalized+hashed) → `Journal.Approve` (approver = accepting user; `payload_hash` pinned) → `Journal.BeginExecute` (written BEFORE the broker push; `idempotency_key` = the effect UUID, stable across retries) → the broker push → `Journal.Succeed`/`Fail`. Owner-attributed (`Proposal.UserID`, 15.6). **High tier** — the S01.9 PIN step-up is enforced at the API/answer layer (the §9 approvals-family call), consistent with the intake approvals family; this packet composes the journal transitions, the step-up wiring point is named (seam §2).
- **R8.** **Broker CAS push** (S13.6 step 4): `git push --force-with-lease=<ref>:<sha-at-approval>` — the **bare `--force-with-lease` form is forbidden** (trivially defeated by background ref updates, P-T12-1); multi-ref updates use **`--atomic`**. A **lease failure** (git rejects: the ref moved since approval) is a **normal collision → back through R4 to a merge card**, **NEVER a blind retry against a new sha** (S13.6 step 4 verbatim). Distinguish from the class-A crash-window: a crash mid-push leaves an in-doubt `executing` row that `ReconcileInDoubt` replays **blind against the SAME pinned expect-sha** (safe — ref-level CAS, S02.7 class A); a lease **rejection response** from git is a definitive collision, not a crash → `Fail` + merge card. Pacing respects GitHub's documented ≤6 pushes/min/repo and 2 GB cap (household volume is orders below; a note, not a gate).
- **R9.** **On accept success**: the deliverable state moves **→ `accepted`** via a NEW `internal/review` state verb (storage+eventlog only, §22 — the enum `StateInReview`/`StateAccepted`/`StateSuperseded` and the "Accept mechanics are Spec S13.6's" comment already exist in `review.go`); prior revisions/deliverables superseded per S13.1. The accept success **fires the S02.8 sibling-accept freshness trigger** to active runs in the project (R16).

### C — S13.6 broker git verbs + P-T12-1 (the broker is the guardrail)

- **R10.** **The broker gains git verbs** (S13.6; S11.5 — the broker "executes with the owner's credential OUTSIDE the sandbox and returns only the result"): a push op that runs `git push` with the **broker-held SSH key** (ssh-agent posture — the key **NEVER leaves the broker**, `GIT_SSH_COMMAND`/agent-style), and an SSH-signing op (R12). Extend the existing wire protocol (`internal/broker/wire.go` `Op*` constants + `Request`/`Response`; `broker.go` `dispatch`; `store.go` credential kinds; `client.go` methods). The broker imports **only stdlib + `golang.org/x/sys/unix`** today (verified) and MUST stay DB-free — therefore the **protected-ref policy travels as request data**: the control plane reads it from `project.Store.ProtectedRefs(ctx, projectID)` (B4-2, §23) and hands it to the broker on the push request. The SSH git key is a new stored credential kind (or the `signing-key` kind extended); credential hygiene (`0700` store, host-only, audience-bound AEAD) is unchanged (§12).
- **R11.** **P-T12-1 — THE BROKER IS THE GUARDRAIL** (S13.6, tested): as a security property — member git credentials exist **ONLY inside the broker**, never enter sandboxes, never exported (D2; the sandbox never receives the broker git UDS — empty-env deny-by-default, §12; outward git effects route via the 4.2 gated proposal → effect journal → control-plane broker call, so the sandbox is a non-participant in the push). The broker **refuses any push to a protected ref that does not originate from an approved accept effect** (default protected set = the project's default branch, "main only via accepts", S13.6/S13.7); every broker push is **CAS** (bare force forbidden, R8). **Conformance-suite entry (mandatory, P-T12-1):** a non-accept push to a protected ref **MUST observe a broker-side refusal** — a standing test in `internal/broker`. The exact accept-authorization wire (a token/marker the control-plane accept path is the sole setter of; the broker verifies the target ref against the passed protected set and refuses a protected-ref push lacking authorization) is executor discretion **within these invariants** — do not weaken any of: broker-only keys, CAS-always, protected-ref-requires-accept-authorization, the refusal test.
- **R12.** **SSH signing** (S13.6 step 5; G2 D2.6): the **broker performs signing** (`gpg.format=ssh`; the key never leaves it — R10). The **operator SSH-signs from day one**; members opt in at enrollment. **All-or-nothing per user** — a user whose commits are not all signed MUST NOT enable vigilant mode; enforce structurally (a user's signing posture is consistent; the platform never produces a mixed-signed state that would break vigilant mode). **gitsign/Sigstore is NEVER used** (renders Unverified on GitHub — worse than no signature): no `gitsign` string exists in the package (a source-scan conformance assertion, the §23 tripwire precedent). No GitHub Pro at v0.
- **R13.** **Enrollment steps are DOCUMENTED, not auto-executed** (S13.6 step 6; one-time per member): keypair generated **inside the person's store on the host** (never leaves it, store hygiene §12), the user uploads the pubkey to their GitHub account (auth + optionally signing) — **operator hands-on** (FLAG §10), the ID-based noreply address is captured into the store, repo owners invite collaborators, owner-exit = repository transfer (1-day acceptance; stored remotes rewritten, redirects never trusted). At v0 single-user the operator is the only enrollee. The brief documents the sequence; the platform automates only what is host-local (keypair generation in the store).

### E — S13.10 Platform-state snapshot pipeline

- **R17.** **Pipeline, per scheduled snapshot** (S13.10; S02.9): the **S02.9 durable set** (the S02.2 table set, now incl. `snapshot_ledger` + the S13.9 link) → **`VACUUM INTO`** a temp file (consistent against the live DB, S02.9) → **text-first `.dump`** (diffable; **raw `run_events` payload bodies past the 11.1 compaction horizon excluded** — full traces stay local, S02.9/S13.10) → **plus the platform's git-versioned file stores** (worker templates [S08], knowledge/memory files [S09]) as **text-first exports** → **`tar | zstd | age -r <operator recipients>`** → **ONE encrypted blob per snapshot** → committed to the **operator-owned private snapshot repo** (D9), **keep-N on one branch** (⚙ `backup.keep`), **pushed CAS by the broker** (R10 — the same broker push path; the snapshot repo's own protected ref). `tar` = stdlib `archive/tar`; `zstd`/`age` = Go modules (R25/R26).
- **R18.** **Client-side encryption is UNCONDITIONAL** (S13.10): nothing leaves the host unencrypted (a private repo is access-controlled, not end-to-end encrypted, and the payload includes every member's memories and receipts). **Secrets are NEVER in the snapshot payload** (S13.10; G2 D2.5): per-person credential stores and broker secrets ride the broker's own at-rest mechanics — their backup/escrow is a **broker duty, deliberately decoupled** from this pipeline. The pipeline reads platform.db + the git-versioned file stores only, never the broker store.
- **R19.** **`snapshot_ledger` integrity is load-bearing** (P-T12-4; S13.10): age has NO sender authentication — encryption proves who can read, never who wrote. Every snapshot's **SHA-256 + size + created-at** is recorded in **`snapshot_ledger` (platform.db) AND inside each SUBSEQUENT archive** (the durable set membership, R1/R17 — so archive N+1 carries archive N's ledger row; a compromised remote swapping a blob is defeated by the ledger check, nothing else). **Blob discipline:** stay under GitHub's enforced **100 MB file limit** — chunk the archive at ~90 MB if ever needed; pushes sit far below the 2 GB cap (S13.10).
- **R20.** **Identity + recipient are consumed FROM THE FILE PATH**, never from code/tests/prose (operator directive; escrow DONE 2026-07-22, `P3/STATE.md` item 6): the escrow ceremony placed the live identity at **`~/.config/sinet/age-identity.txt`** (`0600`) with the recipient public key **derivable from it**. The pipeline reads identity/recipient from a **config path** whose default is that file (a settings/bootstrap value, resolved at runtime); the recipient is derived at runtime (age Go module identity→recipient). **NEVER hardcode key material** in code, tests, or committed prose (the pubkey string is not to be pasted anywhere in the packet). The platform adopts the **age Go MODULE** (R25), not the age v1.3.1 CLI (which is user-level ceremony tooling only).
- **R21.** **Cadence rides S01.7 PERSISTENT CALENDAR TIMERS, not an in-process ticker** (S01.7 verbatim: "Platform-internal schedules (snapshots, quarterly passes, canaries) run as system-manager calendar timers with `Persistent=true`, so a slot missed in suspend fires once on next activation" — distinct from the WAL-truncate / recovery-sweep in-process tickers, which may miss during suspend). The snapshot is a **one-shot invocation** (a new `sinet` subcommand/mode — the CLI mode table `internal/cli`), driven by a **GENERATED** `sinet-snapshot.timer` + `.service` (Persistent=true; the interval derives from ⚙ `backup.interval`) via `internal/units`, **generated-never-installed** (the B0 precedent; host install = the B4 gate/hardening session). keep-N per ⚙ `backup.keep`. **`backup.repo_rotation`** (annual snapshot-repo rotation, P-T12-3 mitigation) is **referenced, not consumed at v0** — the rotation act (create a fresh private repo, archive the old, re-point) is an **operator ceremony/hands-on** step (FLAG §10; auto-creating a remote repo is never coded, matching the dev-mode no-network-creation posture); a rotation-due surface is an optional thin add, not required.

### F — S13.10 Restore drill (backup that is not restore-tested does not exist)

- **R22.** **Restore drill — scheduled and TESTED** (S13.10; ⚙ `backup.drill_interval`; generated `sinet-restore-drill.timer`/`.service` per R21): **fetch** the newest blob from the remote → **verify against the ledger** (**FAIL-CLOSED on mismatch** — the drill aborts and raises a **High flag**, S14 seam) → **decrypt with the ESCROW identity** (from the identity path, R20 — proving the recovery material, not just a live-session key) → **unpack** → **rebuild the DB from the dump** → **`integrity_check` + the S02.9 invariant assertions** (integrity ok, gap-free `event_seq`, durable-set consistency — the S02.9/§8 invariant family). The **drill result is an event-log record either way** (S13.10). A rebuild happens into a scratch location — the live DB is never touched by the drill.
- **R23.** **Dev-mode: ALL git legs against LOCAL BARE-REPO FIXTURES** over the `file://` transport (the §23 hermetic core already sets `GIT_ALLOW_PROTOCOL=file`): the accept push, the snapshot push, and the drill fetch all run against `t.TempDir()` bare repos — a real `git push`/`fetch` exercising the exact CAS `--force-with-lease` + `--atomic` path at **full fidelity except no network**. Tests use a **fresh temp age keypair** generated in `t.TempDir()` (via the age Go module) for encrypt/decrypt round-trips — **the real identity file is never read by tests**. **Zero network anywhere in tests; zero paid engine calls anywhere in the packet** (packet constraint; CONVENTIONS §3).
- **R24.** **The LIVE first snapshot push is a BRING-UP step (S19.6), scoped precisely, NOT an executor-subagent action** — it is UNBLOCKED by the completed escrow (item 6) but gated on **two operator hands-on prerequisites** (FLAG §10; never assumed by the code): **(a)** the operator **designates/creates the private snapshot repo** and records its remote URL (config/registry); **(b)** the operator **enrolls the git SSH key** for that repo into the broker (R13 enrollment). The executor's code MUST make the live leg **pure configuration** — remote URL + broker key — with **no code change** needed to go live. Once both prerequisites exist, `sinet snapshot` run once produces the encrypted blob → the broker CAS-pushes it to the private repo → a `snapshot_ledger` row lands; the drill then proves recovery with the escrow identity. The brief documents this; the executor does not perform a network push.
