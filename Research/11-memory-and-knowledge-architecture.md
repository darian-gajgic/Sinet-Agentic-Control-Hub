## 2. Current state of the art (mid-2026)

### 2.1 The memory-system market has an evidence problem — and its own leaders are converging on files

The dedicated-memory-system category (mem0, Zep/Graphiti, Letta, LangMem) is commercially loud and evidentially weak:

- **The category's headline benchmark collapsed under audit.** LoCoMo — the number every vendor leads with — has ~6.4% corrupted answer keys (99/1,540) and an LLM judge that accepted ~63% of intentionally wrong-but-on-topic answers (Penfield Labs audit, 2026-04) [S1]. The mem0-vs-Zep public dispute produced scores of **58.44%, 65.99%, 75.14%, and 84% for Zep on the same benchmark**, depending on who ran it and under which configuration: Zep's own 84% headline was an arithmetic error it later corrected to 75.14% ("we erred in how we calculated Zep's LoCoMo score"); mem0's adversarial recalculation got 58.44%; mem0's original Zep score (65.99%) rested on SDK-gap misconfiguration; Zep has since published a new 80% figure (2025-12), which changes nothing about the dispute's lesson [S2, S3]. An independent synthesis ("The Benchmark Theatre," 2026-05) documents the pattern across the leaderboard — vendor-run evals of competitors, lenient judges, LongMemEval-S fitting inside a modern context window — and recommends exactly what this campaign already does: "Ignore published leaderboards… test full-context and grep baselines on your own data" [S4]. mem0's own README numbers moved from 68.5 to a claimed 92.5 on LoCoMo between April 2025 and April 2026 with no independent replication — within ~1 point of the audited ceiling [S5].
- **Letta measured a plain filesystem beating the memory vendors on their own benchmark class** — 74.0% on LoCoMo with gpt-4o-mini "by simply storing conversation histories in files," above mem0's then-best 68.5% — and published the conclusion against its own category's interest: "current memory benchmarks may not be very meaningful"; memory is "more about how agents manage context than the exact retrieval mechanism used" [S6]. (Vendor-blog tier but contra-interest, which raises credibility.)
- **The pioneers are migrating to Sinet's shape.** Letta — the company that invented agent-managed memory blocks (MemGPT) — shipped "Context Repositories" (2026-02, its Letta Code memfs feature): memory as **git-versioned plain files with automatic commits** ("every change to memory is automatically versioned with informative commit messages"), subagents in isolated git worktrees, merges via standard git conflict resolution [S7]. ChatGPT memory — the largest consumer memory deployment — is, per two independent reverse-engineerings, **not vector retrieval at all**: curated facts, AI-written user-knowledge summaries, and recent-conversation summaries injected wholesale every prompt [S8]. Anthropic's GA memory tool is client-side and file-based (Claude requests file ops; the application executes and stores) with first-party guidance prescribing expiration and size caps [S9]. Claude Code's auto-memory is deterministic files under a hard load budget (MEMORY.md index, "first 200 lines… or the first 25KB, whichever comes first," overflow to on-demand topic files) [S10].
- **Operational reality of the sidecars:** self-hosted mem0 is three containers (API, Postgres+pgvector, Neo4j) — "two stateful backends to back up, version and keep highly available" — and its LLM reconciliation step is a documented silent-corruption vector ("A wrong UPDATE or DELETE silently corrupts memory"); a filed reproduction showed it substituting the current date for dataset timestamps, permanently storing wrong facts [S11, S12]. Graphiti (Apache-2.0, healthy) historically required an external graph DB server (Neo4j 5.26+/FalkorDB/Neptune/Kuzu) plus a structured-output-capable ingestion LLM ("smaller models may produce unreliable structured outputs"); by mid-2026 an embedded FalkorDB-Lite install ships (`graphiti-core[falkordblite]`) and the Docker/FalkorDB packaging gap was fixed 2026-06 — the infra objection has softened; the per-ingestion LLM cost and the trust model have not [S13]. LangMem remains pre-1.0, LangGraph-coupled, with thin production evidence [S14]. The most honest summary in the comparative literature: "Memory frameworks are not winning on accuracy. They win by cutting a full-context response from 17 seconds and 26,000 tokens down to 1.4 seconds and 1,800 tokens, at a real cost in accuracy" [S11] — a trade Sinet does not need at a registry-sized corpus.

### 2.2 Deterministic-first vs vector-first: the evidence, with its boundaries

The strongest 2026 evidence, ranked:

- **Controlled, on memory-shaped data:** "Is Grep All You Need?" (arXiv 2605.15184, 2026-05; unrefereed preprint, weighted accordingly) evaluated coding-agent harnesses on a 116-question LongMemEval sample across Claude Code, Codex, Gemini CLI, and a custom harness: "Grep generally yields higher accuracy than vector retrieval," and harness/tool-calling style dominates outcome variance [S15]. SWE-Explore (arXiv 2606.07297, 848 issues/203 repos) finds agentic multi-step exploration "a clear tier above classical retrieval" — the failure mode of both BM25 and dense retrieval is the *one-shot mode*, which an iterating agent with grep-class tools routes around [S16].
- **The strongest pro-embedding production result defines its own boundary.** Cursor's semantic-search A/B (2025-11) — the only rigorous production evidence that embeddings help coding agents — shows +12.5% average QA accuracy (6.5–23.5% by model), but the code-retention gain concentrates in codebases with 1,000+ files (+2.6% there vs +0.3% overall), required an embedding model custom-trained on millions of agent session traces, and even then "our agent makes heavy use of grep as well as semantic search, and the combination… leads to the best outcomes" [S17]. Neither the scale nor the training investment maps to Sinet's corpus.
- **The concession from the pro-vector side is explicit.** LlamaIndex's rebuttal to grep-maximalism (2026-05) states grep's validity conditions verbatim: "A text corpus is available, typically as a filesystem of text-based files. The corpus is small (hundreds to thousands of documents)" — and stakes the semantic claim on web-scale corpora, PDFs/images, and vocabulary mismatch [S18]. Sinet's knowledge corpus (curated playbooks, style guides, lessons, conventions — text by construction per 11.3) satisfies every condition with an order of magnitude of headroom. Milvus's own rebuttal concedes: grep is "fast, exact, and — most importantly — predictable… today's embeddings are still too fuzzy to trust" [S19].
- **Field practice:** Anthropic removed vector-index RAG from Claude Code early on (agentic search "outperformed everything, by a lot" — credible first-party claim, never published as data) [S20]; Augment's top-tier SWE-bench agent used only grep/find [S21]; Sourcegraph dropped embeddings for Cody Enterprise on operational grounds (index build/refresh/drift), replacing them with adapted BM25 with no reported quality regression [S22]; Aider ships a fully deterministic tree-sitter+PageRank repo map [S23]. The counter-cases are real but out of Sinet's regime: EA reports grep-class assistants as "noise" on a multi-million-line C++ monorepo (hit-count explosion) [S24]; the cost-curve synthesis places the crossover at mega-monorepo scale or scarce context budgets, because "maintain_cost × time" — the index pipeline — dominates vector-first total cost [S25].
- **At household scale the shipped state of the art is not retrieval at all but curated injection** (ChatGPT full-injection memory [S8]; CLAUDE.md/AGENTS.md session-start injection; long-context research showing full-context beating RAG on quality for strong models, the objection being cost not accuracy [S26]). And the incremental escape hatch is cheap: SQLite FTS5 runs sub-millisecond at thousands-of-records scale inside the store Sinet already owns, and FTS5+sqlite-vec hybrid via reciprocal-rank fusion is a ~200-line add-on, not an architecture change [S27]. Local embedding models are no longer a cost barrier (nomic-embed-class models run on CPU; Qwen3-Embedding-8B at Q4 outscores OpenAI's API embedding on MTEB) [S28] — which sharpens the decision: the argument against vectors here is **maintenance, auditability, and reproducibility, not model access** — exactly the term the operational evidence says dominates.
- **Gap flagged honestly:** no published corpus-size threshold ("embeddings needed above N docs") exists, and no controlled ablation targets tens-to-hundreds-of-documents curated corpora specifically. The nearest proxy is [S15] (LongMemEval-scale conversational memory), which favors grep.

### 2.3 Layered lifetimes and defined writers: the prior art is real and the enforcement lesson is sharp

- **The taxonomy is settled vocabulary.** CoALA's working/episodic/semantic/procedural split (2023, the root every survey builds on — flagged old) [S29]; the December 2025 flagship survey (arXiv 2512.13564) makes the lifecycle explicit — Formation → Evolution (consolidation & forgetting) → Retrieval — with "experiential memory (insights & skills)" as a distinct function [S30]. Sinet's scratch/experience/rules layering (S4.2) is a clean instance of this consensus, not an invention.
- **Write-permissioned layers ship today, enforced by capability withholding, not prompts.** Letta memory blocks carry `read_only: true` ("the agent cannot update the block"); its sleep-time architecture goes further: **the primary agent has no memory-editing tools at all** — a separate consolidation agent owns every core-memory write [S31, S32]. Claude Code runs a live two-writer split (human-curated CLAUDE.md vs agent-written MEMORY.md) but enforcement is conventional — nothing technically stops the agent editing CLAUDE.md [S10]. The June 2026 memory-security survey (arXiv 2604.16548) formalizes the spec's exact rule as named governance primitives: **"Write Authorization"** (every long-term write attributable to an authenticated source passing an explicit authorization check), **Provenance Visibility, Principal-Scoped Retrieval, Rollbackability, Verified Forgetting** — and flags Store/Share/Forget-Rollback as under-studied [S33]. **No surveyed work distinguishes schema-level from prompt-level enforcement — S4.3 enforced in the schema is ahead of surveyed practice, and Sinet's sole-writer control plane (report 08) makes it nearly free.**
- **Agent-written memory that steers later behavior measurably self-reinforces errors.** The ACL 2026 empirical study (arXiv 2505.16067) names the mechanism — the "experience-following property": similar input → the agent replicates the retrieved memory's output, so "inaccuracies in past experiences compound and degrade future performance"; **selective addition + deletion beats naive add-all growth** — the v1 preprint's abstract put the combined effect at ~10% average absolute, a sentence dropped from the camera-ready; the published tables show per-benchmark gaps of roughly 15–25 pp for strict-selective vs add-all, task-dependent (verification-corrected: direction is solid, the single headline number is unstable) [S34]. MINJA (NeurIPS 2025) weaponizes the same loop: memory poisoning **through ordinary queries alone** — the attacker never touches the store; every poisoned record is generated by the agent itself from crafted inputs — at 98.2% injection success / 76.8% attack success, with utility drop <2% on three of four testbeds (−10% on MMLU), bypassing input/output moderation [S35]. A-MemGuard's countermeasure design is itself a write-permissioned pattern: consensus checks plus a segregated quarantine store [S36]. Together these are the empirical justification for 8.1's gate: an ungated experience-to-behavior path is both a quality defect and an attack surface.
- **Forgetting mechanics split into two families, both with production form:** *hard* expiry at the datastore level (Redis's official agent-memory guidance: TTL'd session memory the model cannot opt out of [S37]; mem0 `expiration_date` auto-exclusion [S38]) and *soft* invalidation preserving history (Zep/Graphiti's bi-temporal model: contradicted edges get `t_invalid` set, "marked invalid rather than deleted" [S39]). A 2026 architectural study adds that **where forgetting control resides** (agent-initiated vs externally triggered) measurably shapes outcomes — forgetting is a control-plane design decision [S40]. And curation is a measured performance feature, not hygiene: beyond [S34], secondary reports describe add-all agents degrading from 39% to 13% accuracy as records grew 248→2,400+ (direction corroborated, magnitudes single-source) [S41].

### 2.4 Gated learning: shipped, but rare — and one high-profile retreat

- **Devin Knowledge is the working production template for propose→approve.** Devin "automatically suggest[s] Knowledge to remember based on your feedback in chat"; suggestions become stored Knowledge through a human save/edit/regenerate/dismiss step (the docs describe the workflow; that un-actioned suggestions are never retrieved is implied rather than stated — verification note); each entry carries a "Trigger Description" (retrieval scope) and a pin scope (no repo / one repo / all repos); retrieval is selective ("Devin retrieves Knowledge when relevant, not all at once") [S42]. This is 8.1/S4.7's exact interaction shape, shipped. Gap: Devin does not surface per-item author/origin — origin-visible cross-user adoption (8.8) exists nowhere found.
- **Cursor shipped auto-proposed Memories (June 2025) and removed them by 2.1 (2025-11-21)** — the official changelog is silent; removal is evidenced by the disappearance of the Memories docs page and community threads — leaving explicit rule files (and, into 2026, agent skills) as its persistent-instruction surface [S43]. The one mainstream coding IDE that tried auto-proposed memory retreated to human-authored versioned files: a cautionary datapoint for proposal-quality economics, not against gating itself.
- **Consumer assistants are post-hoc editable, not pre-approval gated** (ChatGPT: opt-out, delete-with-30-day-log; Claude: viewable/editable memory summary, incognito, project-scoped memories) [S44, S45] — the gate Sinet needs is stricter than consumer practice and matches the enterprise knowledge-management lineage instead: **Guru's verification workflow** (named human verifier per card, expiry intervals 30d–1y or never, anyone-can-flag-unverified, AI-proposed status changes logged for human oversight) is the mature lifecycle template [S46].
- **Research-side distillation exists but ungated:** ACE (arXiv 2510.04618, ICLR 2026) treats contexts as "evolving playbooks" via Generator/Reflector/Curator over **itemized bullets with incremental delta updates** — explicitly to avoid "brevity bias" and "context collapse, where iterative rewriting erodes details over time" (+10.6% on agent benchmarks) — but its Generator/Reflector/Curator loop is fully automated: it "could adapt effectively without labeled supervision," and no human gate appears in the design [S47]. Its representation (itemized, delta-updated entries) is exactly what makes a human gate and per-item removal cheap to bolt on. GEPA/DSPy consumes textual feedback but has no approval gate — any Sinet use would wrap it offline behind the same proposal queue [S48].
- **Proposal-quality economics are qualitatively documented, quantitatively absent.** No published acceptance-rate data exists for Devin suggestions, Cursor memories, or ChatGPT auto-saves. The approval-fatigue literature gives design rules with numbers: risk-calibrated gating (escalate ~5–15% of events), batch review of coherent sets, one-keystroke rejection (asymmetric cost drives rubber-stamping — "approving requires one keystroke; rejecting demands understanding and articulation") [S49]. This composes with report 03's rubber-stamp findings (P-T05-2) and S3.2's risk-ranked inbox.

### 2.5 Provenance and reversibility: tracing is practice, unlearning is not

- **Machine unlearning is not production-ready in 2026** — per the 180-paper survey: retraining "computationally expensive and impractical," definition and evaluation of unlearning an open challenge, architectural methods circumventable ("deactivating these components… allowing the recovery of unlearned content") [S50]. The design consequence — this report's inference, not the survey's recommendation — is structural for Sinet: **keep lessons out of weights entirely** (no fine-tuning in the learning loop); then removal = stop injecting, which is exact and free. Retrieval-side memory is the *reversibility mechanism*, not just a storage choice.
- **Per-run injection logging is infrastructure practice** (mem0 ships `MemoryAccessLog`/`MemoryStatusHistory` tables; 2026 security guidance treats injection logs as the forensic trail for detecting and undoing bad memories) [S51], and PROV-AGENT (2025-08) demonstrates the query shapes a removable-lesson design needs ("Which downstream outputs were affected by a specific agent interaction?") [S52] — **but no shipped product surfaces "this lesson influenced these N runs" to users. Genuine white space** — and Sinet already owns the ingredient: report 07's injection manifest logs every injected item with content hash and selector rule per run. Influence tracing is a join, not a new system.
- **Git-as-provenance is sufficient at this scale and is where the field converged** (Letta Context Repositories' auto-commits [S7]; OpenHands skills, Factory droid memory, Copilot instruction generation — all human-authored/committed markdown in repos [S53]). The June 2026 always-on-agents survey confirms the field gap the spec targets: "the literature concentrates more heavily on accumulating and retrieving state than on governing, recovering, or relinquishing it" [S54].

### 2.6 Scoping, isolation, and precedence: the leak evidence and the cleanest articulations

- **Parameter-scoped isolation leaks the moment one call site forgets the identifier.** LangGraph stores namespace by tuple — isolation holds "provided you remember to use it in every call, or else you have a cross-user data leak" (ecosystem's own words) [S55]; mem0 scopes by four identifiers with subtle null-scoping semantics [S56]; **Letta deprecated its Identities feature outright** — "manage user-to-agent mappings in your own application layer" [S57] — a warning that isolation abstractions you don't own get deprecated under you. The mechanisms with can't-forget properties are DB-enforced policy (Postgres RLS with FORCE, session-variable-keyed) [S58] and physical partition (file/DB-per-tenant SQLite — "queries need no tenant filter… cross-tenant reads become impossible at the connection level") [S59].
- **OWASP now codifies Sinet's design as the named mitigation.** The OWASP Top 10 for Agentic Applications 2026 (released 2025-12-09) lists **ASI06 "Memory & Context Poisoning"**; its actual mitigation set (verification against the official PDF) is: **source attribution for stored content, memory segmentation by user session and domain, per-tenant namespaces, trust scores with decay/expiry of unverified memory, and no automatic re-ingestion of the agent's own outputs** [S60] — the last item being 8.1's gate stated as a security control, and the rest mapping one-to-one onto Sinet's provenance fields, scopes, and verification lifecycle. (The often-quoted "different trust levels for short-term vs long-term memory" phrasing traces to OWASP's earlier Agentic AI Threats & Mitigations guide and secondary write-ups, not ASI06 itself — corrected here.) LLM08:2025 (Vector and Embedding Weaknesses) names multi-tenant vector-store context leakage a first-class risk requiring "fine-grained access controls and permission-aware vector and embedding stores" [S61]. MINJA [S35] adds the sharper lesson: shared memory readable by multiple users is an attack channel **even with perfect read-side authorization** — so house knowledge must be gated on *write* (D10 is the right shape), not merely ACL'd on read.
- **Precedence prior art is one sentence long, and the silent-conflict failure mode is documented first-party.** AGENTS.md: "The closest AGENTS.md to the edited file wins; explicit user chat prompts override everything" [S62]. Claude Code's memory docs order managed-policy → user → project → local, concatenated — **with the warning that when two files conflict, Claude "may pick one arbitrarily"** [S10]. That admission is the citable justification for 8.9's rule: precedence must be declared and total, and substantive conflicts must surface as questions because the model's own tie-breaking is nondeterministic.
- **Shared truth under concurrency needs a serialization point, not CRDTs.** At one-host household scale, a single store plus optimistic versioning (version check on update, reject-and-retry) reproduces everything CRDT machinery offers [S63]; Zep group graphs are server-serialized; Devin org Knowledge is a single reviewed store. No strong public design exists for "concurrent workers updating shared project knowledge" — thin spot in the field, resolved below by composition with Sinet's own S1.11/freshness machinery.

## 3. Candidate approaches

**A. Memory-sidecar service (mem0 self-host / Zep+Graphiti / Letta server).**
*For:* purpose-built APIs; graph/temporal features (Graphiti's `t_invalid` supersession is genuinely good design); active ecosystems. *Against:* the accuracy evidence for the category does not survive audit (§2.1); each brings stateful infrastructure and moving parts Sinet doesn't otherwise run (Postgres+pgvector+Neo4j; a graph store plus per-ingestion structured-output LLM; a full agent runtime) against bus-factor-1; LLM reconciliation is a documented silent-corruption vector — the exact opposite of 8.6's "cannot silently accumulate garbage"; agent-writable-by-default trust model inverts 8.1; parameter-scoped multi-tenancy is the leak class §2.6 warns about; binary/graph stores are hostile to 11.3's text-first dump-shaped snapshots; and D6 forbids handing store handles to workers anyway — the platform would wrap every access, paying the sidecar's cost while using none of its autonomy.

**B. Platform-owned: git-versioned knowledge files + SQLite rows in platform.db, deterministic selection, FTS5 as the query mechanism.**
Knowledge documents (playbooks, style guides, rubrics, exemplars, conventions) as markdown files under git (provenance/versioning/rollback = commits); structured entries (lessons, preferences, observations) as owner-attributed rows in the report-08 store; selection stays report 07's registry-driven injection; agent-facing search over knowledge = engines' native grep on mounted slices + an FTS5-backed platform query tool. *For:* matches the convergence line of the strongest practitioners (§2.1, §2.2); schema-level writer enforcement nearly free under the sole-writer control plane; text-first by construction (11.3); provenance = git + rows; zero new services. *Against:* Sinet owns the curation pipeline (but §2.4 shows that pipeline is the product's core anyway); lexical-only retrieval could miss synonymy at corpus sizes Sinet may never reach (post-gate hatch defined in §4.10).

**C. Engine-native memory as the platform mechanism (Claude Code auto-memory / memory tool; opencode community memory plugins).**
*For:* adopt-don't-fork purity; zero build. *Against:* Claude Code auto-memory is an **ungated agent-written store that persists across sessions and steers later behavior — structurally incompatible with 8.1/S4.3** on the very lane it ships on; it is also lane-local (nothing on opencode/GLM), per-project rather than per-user×scope, and version-drifting; the GA memory tool is client-side — Sinet would implement the storage anyway; opencode memory plugins are young third-party code (adopt-don't-fork applies). Use engine-native features only as *harvest sources and lane-local optimizations* under platform policy (§4.9), never as the memory system.

**D. Vector/hybrid retrieval from day one (local embeddings + sqlite-vec or a vector DB).**
*For:* synonymy/cross-lingual recall; local models are free-tier viable now [S28]. *Against:* every condition that makes embeddings pay is absent at Sinet's corpus size (§2.2); non-reproducible assembly and silent wrong-injection conflict with S4.6 trace auditability; index maintenance is the dominant hidden cost; the post-mortem's two-retrieval-philosophies trap. The evidence assigns it exactly the role the harvest map proposed: a post-gate, evaluated addition triggered by measured need.

## 4. Recommendation for Sinet

**Primary: B — a platform-owned, deterministic-first memory architecture: three write-permissioned layers × four scopes, stored as git-versioned markdown plus owner-attributed rows in platform.db, learning admitted only through a proposal→approval pipeline with per-item provenance and injection-manifest influence tracing, forgetting as designed lifecycle, and vector retrieval held behind a pre-registered evaluation gate.** Numbers marked ⚙ are operator-editable settings (G1 rider) proposed for G2 ratification.

### 4.1 The layer model (S4.2/S4.3 made schema)

Three layers, distinguished by **lifetime and writer**, with the writer rule enforced by which actor can reach which table/path through the sole-writer control plane — capability withholding, the shipped enforcement pattern (§2.3), applied at the storage layer where no surveyed system applies it:

| Layer | Content | Writer | Lifetime | Home |
|---|---|---|---|---|
| **L0 scratch** (7.8 instance) | working notes, learned-this-task | the worker | expires with the task | Task Context Ledger section + run workspace (settled, report 07) |
| **L1 experience** (7.8 overlay, D8) | **observations**: compact, *descriptive* run summaries — what was done, what was encountered, what failed (never instructions) | platform distiller (local model) from run evidence; worker may append observation notes | TTL ⚙90d, prunable, distill-then-delete | rows in platform.db, per-user × per-worker-template |
| **L2 knowledge** (permanent) | lessons, preferences, playbooks, rubrics, style guides, exemplars, project truth | **humans only** — every entry enters via an approval (8.1) or is directly human-written | until removed/superseded; verification-expiry per kind | markdown files in git-versioned knowledge dirs + registry/entry rows |

The critical boundary — and this report's resolution of the S4.3-vs-8.1 tension — is **descriptive vs prescriptive**: L1 holds *observations* (facts about what happened, injected only as clearly-labeled history when relevant, never as rules); anything *behavior-steering* (a lesson, a preference, a rule) exists only in L2, and L2 has exactly one write path: the human gate. This is precisely the segmented, trust-scored store ASI06 prescribes — including its ban on automatically re-ingesting the agent's own outputs [S60] — the quarantine structure A-MemGuard validates [S36], and the countermeasure to the measured experience-following failure loop [S34] and MINJA-class poisoning [S35]. Workers never write L2, the distiller never writes L2, helpers write nothing durable at all (their reports land in the coordinator's L0 per D6/report 06).

### 4.2 The scope model and the schema core (15.6 day one)

Scopes are orthogonal to layers: **user** (personal memory, S4.1) · **worker-overlay** (user × template, D8) · **project** (S4.4) · **house** (S4.5). Every memory row/registry entry carries `{owner_user, scope, scope_ref, layer, kind, status}` from day one, even while operation is single-user (15.6). Schema additions to report 08's core (names indicative; DDL at the spec workshop):

- `knowledge_entries` — id, owner_user, scope, scope_ref, layer, kind (`lesson|preference|playbook|rubric|style|exemplar|convention|observation`), title, content (text) or file_ref (path into a knowledge dir + git commit hash), **topic_key** (normalized subject for conflict lookup), selectors (tags: domain, repo/project, task-type, trigger phrases — Devin-style trigger text as *rule input*, not embedding), status (`proposed|active|retired|removed`), version / `supersedes_id`, provenance fields (§4.5), verification fields (`verified_by, verified_at, reverify_interval ⚙`), `expires_at` (L1), `last_injected_at`, created/updated.
- `lesson_proposals` — the queue: evidence refs (run ids, diff refs, comment refs), drafted content, proposed scope/kind, risk rank, batch id, status (`open|approved|edited-approved|dismissed`), decided_by/at. Proposals are **not** memory: nothing reads them into any run context.
- `knowledge_adoptions` — adopter_user, source_entry_id, adopted_entry_id, adopted_at (8.8's by-choice sharing with visible origin; adoption = **copy into the adopter's scope** with `origin` pointing at the source — the mem0-style origin-key giving N13's cross-user dedupe).
- Knowledge **files** live in per-scope git-versioned directories: `knowledge/house/` (operator-owned, D10-gated — N20's content lands here at day one), `knowledge/users/<user>/`, `knowledge/projects/<project>/`; commits are made by the control plane on approval, with the approver as author (D9 attribution discipline). Registry rows carry the commit hash — the row is the selector index, the file is the content, git is the history. Everything dumps text-first (11.3) by construction.

### 4.3 Retrieval philosophy (the tested stance)

**Deterministic-first is ratified by the evidence, with its boundary conditions now explicit.** Selection into runs is report 07's registry-driven rule lookup over the selector fields (settled). Within-run knowledge search is the engines' native grep over the mounted slice plus one platform tool: `knowledge_search` backed by **SQLite FTS5** over entry content, scope-filtered server-side (§4.8) — sub-millisecond at three orders of magnitude beyond Sinet's corpus [S27]. No embeddings, no index pipeline, no similarity ranking in v0: assembly stays reproducible (same task + same registry state ⇒ same slice), auditable (11.1), and cache-stable — the properties the operational evidence says dominate at this scale (§2.2).

**The vector post-gate (pre-registered so the decision is data-driven, not vibes):** every `knowledge_search` miss and every "knowledge existed but wasn't injected" incident (found in retro/verification) is logged as a **retrieval-miss event**. Adding an embedding lane (sqlite-vec + a local embedding model, RRF-fused with FTS5 — the ~200-line pattern [S27]) becomes a candidate only when, post-benchmark-gate (15.3), the miss log shows ⚙≥5% of tasks affected by lexical misses that semantic matching would plausibly have caught, or the corpus exceeds ⚙~5,000 entries. If adopted, embeddings rank *candidates for the trace-manifested selection* — they never silently inject.

### 4.4 The gated learning pipeline (8.1–8.3, S4.7)

Five stations, three of which Sinet already has:

1. **Evidence collection (deterministic, free).** The event log + review machinery already capture the signals N13 named: requester edits (accepted-diff vs draft), review comments, accept/reject verdicts, verification findings, retro notes, and L0 `learned-this-task` content at task end. No new instrumentation.
2. **Proposal drafting.** A local-model pass (permanent free tier) drafts candidate lessons from evidence, applying N14's quality rules: **a LESSON requires a correction** (something went wrong and was fixed — no invented insights); a WIN requires an accepted outcome; drafts carry their evidence refs verbatim. Cap ⚙2 proposals/task; batch into review sets (weekly digest ⚙ + on-demand), risk-ranked, one-keystroke dismiss — the approval-fatigue design rules [S49] and S3.2's inbox mechanics.
3. **The gate.** Owner approves own-scope entries; operator approves house promotions (D10); project entries need the project owner (10.x: everyone approves their own objects). Approval can edit or regenerate the draft (Devin's shape [S42]). Nothing skips this station — including "obvious" fixes; the Cursor retreat [S43] shows what proposal noise does to trust, so the volume knobs live at station 2, never as auto-adoption.
4. **Versioned adoption.** Approval writes the entry (row + file commit where applicable) with full provenance; supersession is a new version with `supersedes_id`, never in-place mutation (report 08's history-never-rewritten rule).
5. **Verification lifecycle (the Guru import [S46]).** Behavior-steering entries get a re-verify interval (⚙ by kind: house playbooks 6mo, lessons 90d, preferences never unless flagged); expiry produces a *review card*, not silent death; any user can flag an entry stale; `last_injected_at` identifies dead weight for pruning proposals. Distillation (8.3) is the same pipeline at a higher tier: when ⚙≥3 lessons share a topic_key, a distillation proposal offers a playbook delta and retirement of the constituents — ACE's itemized-delta representation [S47] with the human gate ACE lacks, i.e., distill-then-delete with approval.

### 4.5 Provenance and reversible influence (8.2, S4.8)

Every L2 entry carries: origin (`proposed-from` evidence refs | `human-direct` | `adopted-from` entry+user | `imported` e.g. N20), proposer (model/version if drafted), approver + timestamp, version chain, and git commit hash where file-backed. Removal semantics, made precise:

- **Removal = status `removed` → the entry leaves every future assembly immediately** (deterministic selection makes this exact — the reason retrieval-side memory is the reversibility mechanism, §2.5). Content stays in git history and the row stays for audit (invalidate-don't-delete, the Zep pattern [S39]); S4.1's personal-data erasure remains available as true deletion (file purge + `VACUUM INTO`'s deleted-content purge, report 08) for the person's own entries.
- **Influence tracing = a join, not a system:** the report-07 injection manifest already records every injected item per run with content hash; `influence(entry) = runs whose manifest contains it`. On removal, the platform surfaces that list with verdicts/receipts — the operator sees what the bad lesson touched and can queue re-verification of still-live deliverables. No shipped product does this (§2.5 white space); Sinet gets it from machinery it already ratified.
- **What removal cannot do** — stated honestly in the UI: accepted artifacts already shaped by the lesson are git history (D9), and unlearning-from-weights is not applicable because lessons never enter weights (no fine-tuning in the learning loop — a standing constraint this report makes explicit).

### 4.6 Scopes in conflict: declared precedence, surfaced questions (8.9/S4.11)

Precedence is **data, not prose**: every injected item carries its scope label in the assembly frame (report 07 §4.3), and the frame's preamble states the total order once — *explicit task spec > project truth > personal (user + overlay) > house defaults* — AGENTS.md-style one-sentence cascade [S62]. Detection of *substantive* conflicts is a write-time job, cheapest at household corpus size: on adoption/edit, the control plane looks up same-`topic_key` entries across the scopes the writer can see, plus a local-model contradiction screen (advisory, free tier); hits create a `conflicts_with` edge and a **question card** to the affected owner — never silent resolution, because the documented alternative is the model picking "arbitrarily" [S10]. Assembly-time: known-conflicting pairs entering one frame get the conflict surfaced in the trace and the question re-raised if unresolved.

### 4.7 One shared project truth (8.7/S4.4) and concurrency

Project knowledge is a **single store with a single serialization point** — the sole-writer control plane over platform.db — plus optimistic versioning on entries (update carries expected version; mismatch → reject-and-retry or question card). No CRDTs, no event bus (§2.6, [S63]). "Immediately the truth for all" composes from ratified machinery: stages assemble fresh from current state (fresh-context-per-stage), so a mid-task update is picked up at the next stage boundary; for long stages, a project-knowledge update emits the same freshness event class as sibling-accept (G1 Def.5), letting active runs re-validate. Interaction with S1.11: knowledge updates are *not* artifact writes — they don't collide with worktree claims; but a plan whose assumptions cite project-truth entries records those entry versions in its freshness fingerprint (report 05 Def.5 extension: add ⚙ knowledge-entry versions for cited entries), so a mid-plan truth change triggers 4.3 re-validation instead of silent staleness.

### 4.8 Multi-user isolation, structurally (10.1/15.6)

Layered so that leakage requires multiple independent failures, with the load-bearing property that **no agent-supplied identifier ever selects memory**:

1. **Selection is server-side by construction.** Assembly resolves scopes from `runs.owner_user` and the task's project — a control-plane join, not a caller parameter (the LangGraph/mem0 forgotten-namespace class [S55, S56] is structurally absent because workers never query the store; D6 already forbids store handles).
2. **The `knowledge_search` tool is scope-bound at the server**: the adapter injects the run id; the control plane derives owner/project and appends the scope predicate itself. The one query path lives in one module with a conformance test that *attempts* cross-user reads (the kill-9-harness discipline of report 08 applied to memory).
3. **Physical partition where it's free:** per-user knowledge *directories* (and per-user sandbox mounts exposing only the owner's slices — S5 composition), so even a path-level escape reads only the owner's files. Per-user DB files were considered and rejected: report 08's single platform.db is ratified, the control plane is the only reader/writer, and cross-scope features (adoption browsing, house knowledge, project truth) would force cross-DB joins the isolation doesn't need.
4. **Write-side gating as the poisoning defense:** MINJA-class attacks ride *reads of shared memory written by others* [S35]; in Sinet nothing a worker writes can reach another user's assembly without a human gate in between (L1 is per-user; L2 is human-gated; house is operator-gated, D10). Adoption is copy-on-adopt (§4.2), so even shared house entries are read-only references and personal adoptions are private copies.
5. **Trust labeling in the frame:** injected items carry scope+origin labels (ASI06's source-attribution and trust-score mitigations [S60]), so a coordinator can weigh house defaults below the user's own instructions — precedence and provenance serve security, not just neatness.

### 4.9 Engine-native memory posture (adopt-don't-fork applied)

- **Claude lane:** auto-memory (MEMORY.md) is **disabled if the pinned version allows it; otherwise contained** — the workspace-scoped memory dir is treated as L0 (wiped with the task workspace) and *harvested*: at task end its content joins the evidence pool (station 1). It never persists as behavior-steering memory (8.1). The GA memory tool stays off in v0 (API-lane feature; its client-side backend would be Sinet's store anyway). **Spike at adapter time: confirm auto-memory disable/redirect mechanics on the pinned version** — and engine memory features join the S2.8 canary suite, because a pinned-version upgrade that ships new memory behavior is a silent 8.1 violation (new platform problem, §7).
- **opencode lane:** no native auto-memory (clean); community memory plugins are not adopted (young third-party code). AGENTS.md/instructions injection stays report 07's mechanism.
- **CLAUDE.md/AGENTS.md files remain the *projection* surface:** per report 07, the platform generates them from the registry; they are never the store.

### 4.10 Forgetting by design (S4.10) — the lifecycle table

| Layer/kind | Mechanism | Default ⚙ |
|---|---|---|
| L0 scratch | deleted with task workspace (report 08 GC); ledger `learned-this-task` archived into the task record only | task end |
| L1 observations | TTL expiry + distill-then-delete: periodic local-model consolidation proposes distillations (→ gate) and deletes the residue | 90d |
| L2 lessons/preferences | never TTL-deleted; verification-expiry → review card; `last_injected_at` staleness → pruning proposal | re-verify 90d (lessons) |
| L2 house playbooks/rubrics | verification-expiry (operator card); superseded versions retired, not deleted | re-verify 6mo |
| Removed/retired entries | out of assembly instantly; audit row + git history retained; true-delete on owner request (S4.1) | — |
| Injected-slice budget | per-scope token budgets within the report-07 stage frame; over-budget → distillation proposal, not silent truncation | ⚙ per scope |

The budget line is the anti-landfill enforcement: the evidence says curation is worth double-digit percentage points [S34], and a hard injected-size budget converts bloat from a silent quality tax into a visible curation task — the Claude Code 200-line/25KB discipline [S10] generalized.

### What would change the decision

1. **Retrieval-miss data crossing the §4.3 gate** — adds the local-embedding RRF lane (evaluated, trace-manifested), not a memory sidecar.
2. **A memory system shipping schema-level write authorization + human-gated writes + text-first storage** as first-class features — re-evaluate as a component behind the same contract; none exists mid-2026 (§2.3, §2.4).
3. **An independent, uncorrupted benchmark showing graph-memory beating curated files on *task work* at small scale** — the current benchmark class cannot support that claim (§2.1); a working temporal-supersession need at household scale (years of contradicting facts) would first be met by `supersedes_id` + `t_invalid`-style status fields (the Zep pattern in plain SQL) before any graph DB.
4. **Engine-native cross-session memory arriving on both lanes as configurable, gateable primitives** — could absorb L0/L1 mechanics; the gate and L2 stay Sinet-owned regardless.
5. **Household scale-out** (many users/projects, corpus ≫ thousands of entries) — revisits FTS5-only search and the weekly proposal digest cadence, not the architecture.

## 5. What NOT to use and why

- **mem0/Zep/Letta-class memory sidecar as the foundation** — discredited benchmark basis, stateful infra against bus factor 1, LLM-reconciliation silent corruption, agent-writable trust model inverting 8.1, parameter-scoped tenancy (the leak class), snapshot-hostile stores. The anti-harvest stance holds (§6).
- **Vector retrieval in v0 assembly or memory search** — every condition that makes it pay is absent; costs land exactly where Sinet is weakest (index maintenance, non-reproducible assembly, silent wrong-injection). Held behind the §4.3 pre-registered gate.
- **Ungated agent-written durable memory in any form** — including engine auto-memory features on their default settings, "self-improving" loops (ACE/GEPA ungated mode), and rolling summaries that steer behavior. The measured experience-following loop and MINJA are the evidence; 8.1 is the rule.
- **LLM-reconciliation of memory (auto UPDATE/DELETE of existing entries)** — mem0's documented silent-corruption class; Sinet supersedes by versioned proposal through the gate instead.
- **Fine-tuning as the learning mechanism** — makes removal impossible (unlearning not production-ready); everything Sinet learns stays in retrievable, injectable, removable text.
- **Per-user separate databases for memory** — isolation is already structural via the sole-writer control plane + server-side scoping; separate DBs break adoption/house/project features and contradict report 08's ratified single-store design. (Per-user *directories* for knowledge files: yes.)
- **CRDTs/event-bus machinery for shared project truth** — single serialization point + optimistic versioning suffices at this scale.
- **Auto-sharing of lessons across users, or silent precedence resolution** — 8.8/8.9 are explicit; the documented alternative is arbitrary model tie-breaking and cross-user contamination.
- **Letta-style identity abstractions or any external system's tenancy model as the isolation boundary** — Letta deprecated its own; Sinet owns the isolation layer.
- **Trusting memory-system leaderboard numbers (LoCoMo-class) for any future memory decision** — the benchmark class is broken; Sinet's own added-value benchmark (11.2) is the only decision-grade instrument.
